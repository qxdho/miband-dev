# 研究历程与误判

<StatusBadge status="sourced" verified="2026-10-25" />

结论：九条误判中有七条来自同一个认知陷阱，把「没有观察到」当成「不存在」。记录这些误判的价值不在检讨，而在于每条误判都指出了证据的边界：被推翻过的结论，比未经检验的结论更能说明当前判断的可靠程度。

## 时间线

| 阶段 | 主张 | 结局 |
| --- | --- | --- |
| 一 | 「10 Pro 的快应用没有网络」 | 修正为「有网络栈、缺 tun 驱动」 |
| 二 | 「9 Pro 支持 fetch，10 Pro 不支持」 | 两者都有 fetch，差别不在代码 |
| 三 | 「需要第三方网桥才能上网」 | 用户否决：那正是要替代的东西 |
| 四 | 「官方 App 提供网络是幻想」 | 证伪：Miwear NET 真实存在 |
| 五 | 「10 Pro 根本没有通路」 | 证伪：通路在，卡在 `/dev/tun` |
| 六 | 「只能等厂商修」 | 证伪：Canopus 模块可以补 |
| 七 | 「要移植 9 Pro 的驱动文件」 | 修正：没有文件可移植，要从源码编译模块 |

## 误判一：把 `getType: "none"` 当成没有网络

严重度：高。状态：已推翻。

**当时判断**：探测脚本输出 `system.network.getType() === "none"`，据此认定手环没有网络接口。

**当时依据**：`getType` 返回 `none`，字面含义就是没有网络类型。

**为什么错**：`uv_netstatus` 只枚举物理接口，类型表为：

```
wifi  wlan0  wlan1  cellsurf  cellular  bt-pan  bt-net  tun0  tun  eth0  ethernet
```

`tun` 确实在表里，但前提是有人调用 `netdev_register` 把 tun 注册进去。没有注册时，表里没有这个接口，`getType` 自然返回 `none`。正确含义是「没有已注册的网络接口」，不是「没有网络能力」。前者说明缺一个驱动注册动作，后者说明硬件或协议栈不存在。

**纠正**：`getType` 是注册表快照，不是能力探测。判断能力需要看其他证据。

**认知陷阱**：接口的返回值反映当前注册状态，不反映潜在能力。一个 API 报「没有」，可能只是「还没有人登记」。

## 误判二：9 Pro 包里没有应用镜像

严重度：高。状态：已推翻。

**当时判断**：9 Pro 的 `firmware/9pro/fw9pro.bin` 里找不到 `vela_ap.bin`，只有 bootloader 和触摸固件，因此无法与 10 Pro 对比。

**当时依据**：用 `unzip -l` 和 Python `zipfile` 都打不开；文件尾没有 `PK\x05\x06`（EOCD）；扫描 `PK\x03\x04` 命中 259 处，但没有一条能通过校验。

**为什么错**：该包只写本地文件头，不写中央目录。所有标准解析器都从 EOCD 入口查找，找不到就报「不是 zip」，但数据是完好的。顺序扫描 `PK\x03\x04` 并逐条 inflate，可以完整解出 258 条，包括 `vela_ap.bin`，大小 7,775,288 字节。

当时的校验标准是「能否组成合法的中央目录」，而不是「inflate 是否成功」。判据选错，导致一个完好的包被当成损坏文件。

**纠正**：编写 `tools/zip_no_cd.js`，以逐条 inflate 成功作为判据。

**认知陷阱**：「标准工具打不开」和「文件坏了」是两件事。先问工具按什么规则找入口，再问数据在不在。

## 误判三：字符串计数 0 等于函数不存在

严重度：高。状态：已推翻。

**当时判断**：10 Pro 的 `vela_ap.bin` 里 `netdev_register` 字符串计数为 0，而 9 Pro 为 1，所以 10 Pro 没有这个接口，无法注册网络设备。

**当时依据**：字符串搜索是最直接的证据，计数为 0 就代表名称没有出现在固件里。

**为什么错**：Canopus 的 3.101.043 target pack 明确记录：

```
netdev_register   entry 0xc1fc214   callable 0xc1fc215   int(void *, int)
```

函数在，地址在，只是名字字符串被裁掉了。固件为节省空间剥掉符号名，只保留地址表。字符串计数为 0 只说明名称未保留，不能说明函数不存在。

**纠正**：字符串计数只能证明存在，不能证明不存在。要证明不存在，需要查符号表、重定位表，或反汇编目标地址确认是否有 `push {..., lr}` 一类的函数序言。

**认知陷阱**：否定性结论需要更强的证据。「找到了」是充分证据，「没找到」只是弱证据。

## 误判四：以为走的是蓝牙 PAN

严重度：中。状态：已推翻。

**当时判断**：手环通过蓝牙 PAN（BNEP）与手机组成 IP 网络。

**当时依据**：这是「蓝牙设备上网」最常见的做法；`bt-pan`、`bt-net` 也确实出现在网络类型表里。

**为什么错**：10 Pro 的 AP 里，`bt_sal_*` 函数只有四类：`gatt_client_*`、`gatt_server_*`、`hid_device_*`、`spp_*`。PAN、BNEP、PANU、NAP 全部为 0，也没有 PPP，`pppd` 计数为 0。

真正的机制是 Miwear NET：一条跑在 BLE 上的 TUN 通道。代码位于 `vendor/xiaomi/miwear/bluetooth/app/app_net.c`，日志字符串为：

```
[Miwear NET Connected]
failed to open /dev/tun: %d
ioctl TUNSETIFF failed: %d
Created Tun: %s
```

完整通路是：快应用 → libuv → TCP/IP 栈 → `/dev/tun` → `app_net.c` → BLE → 小米运动健康 → 互联网。

**纠正**：通路是 TUN over BLE，不是蓝牙 PAN。

**认知陷阱**：「常见做法」不是证据。类型表里有 `bt-pan` 只说明代码支持这种类型，不说明实际使用的是它。

## 误判五：以为「官方不支持 fetch」已被推翻

严重度：中。状态：已推翻。

**当时判断**：`script.canUse('@system.fetch')` 返回 `true`，所以「10 Pro 不支持 fetch」的说法被推翻了。

**当时依据**：`canUse` 返回真，说明模块可用。

**为什么错**：`canUse` 只回答「这个模块是否编译进固件」，不回答「它能不能工作」。模块在、接口能调、底层没有网络出口时，`canUse` 依然返回 `true`。正确的表述是「模块存在，但可用性未验证」，而不是「不支持的说法被推翻」。

记录中出现过一次自相矛盾：先判断不能据此断定可用，随后又表述为已被推翻。两种说法不能同时成立，后者把模块层的证据错误地扩展到了产品层。

**纠正**：区分三个层次。

| 层次 | 要回答的问题 | 证据 | 状态 |
| --- | --- | --- | --- |
| 模块层 | 模块是否编译进固件 | `canUse` 返回 `true` | 已证实 |
| 权限层 | 调用是否被允许 | 调用能走到 DNS 解析，权限检查在更前面 | 已证实 |
| 产品层 | 是否有网络出口 | `/dev/tun` 不存在 | 已证实，结论为没有出口 |

**认知陷阱**：一个布尔值只能回答一个问题。不要让它替其他层次作证。

## 误判六：拿网桥方案当答案

严重度：中。状态：已推翻。

**当时判断**：编写一个 fetch 兼容层，把请求经 interconnect 转发到手机端接收器，由接收器发出 HTTP 请求。

**为什么被否决**：技术上可行，但用户的目标是替代 interconnect，而这个方案的本质就是 interconnect，只是换了一个 API 名字。用户拒绝时指出，其他网桥方案与这个方案本质相同，而目标正是替代它。

**纠正**：目标不是「让 fetch 能用」，而是「用官方 App 的通道让 fetch 能用」。前者可以使用任何传输方式，后者只能使用 Miwear NET，两者要求完全不同。

**认知陷阱**：先确认「手段」是否被排除在目标之外。把「能用」当成目标、把「用官方通道」当成偏好，方向就会偏。

## 误判七：以为要移植 9 Pro 的驱动

严重度：中。状态：已推翻。

**当时判断**：9 Pro 有 tun 驱动，10 Pro 没有，把 9 Pro 的驱动搬过去即可。

**为什么错**：9 Pro 的 tun 驱动不是一个可搬运的文件，它静态链接在 `vela_ap.bin` 里。9 Pro 的 `modlib`、`insmod` 字符串计数为 0，根本没有模块机制，也不存在可以拷贝的 `.ko`。

真正的路径是用 Canopus 的 SDK 重新编译一个 tun 驱动模块，加载到 10 Pro 上。10 Pro 恰好有完整的模块机制，`insmod`、`rmmod`、`lsmod`、`modlib_*` 全部存在。Canopus target pack 之所以关键，是因为它提供了编译所需的符号地址。

**纠正**：不是移植文件，是重写模块。

**认知陷阱**：「移植」要先问粒度。源码级、二进制级、模块级是三件不同的事。

## 误判八：把 `needNetwork` 当成网络开关

严重度：低。状态：已推翻。

**当时判断**：快应用 manifest 里有 `needNetwork` 字段，打开它可能就能联网。

**为什么错**：`needNetwork` 定义在 `vendor/oss_quickapp/include/quickapp.h:246`：

```c
bool needNetwork;   // APP是否依赖网络 默认false
```

它只是应用元数据，用来在应用商店或权限提示里显示「此应用需要网络」。固件里只有一处引用，位于 `package.cpp` 中 apps.json 的序列化逻辑，没有任何代码根据它去申请网络资源。

**纠正**：`needNetwork` 不触发任何网络动作。

**认知陷阱**：名字像开关的字段，多半只是标签。要证明它是开关，需要找到「读取它并改变行为」的代码。

## 误判九：以为 10 Pro 是阉割版

严重度：高。状态：已推翻。

**当时判断**：10 Pro 相比 9 Pro 砍掉了网络能力。

**为什么错**：对比两代 AP 的框架特征：

| 特征 | 10 Pro | 9 Pro |
| --- | --- | --- |
| JIDL feature 框架 | 21 处 | 0 |
| `fetch_impl` | 11 处 | 0 |
| 模块机制（`modlib`） | 16 处 | 0 |
| `tun%d` | 0 | 1 |
| `netdev_register`（字符串） | 0 | 1 |
| NSH 网络命令（`ifconfig`/`ifup`/`dns`/`dhcp`） | 有 | 未记录 |

10 Pro 是更新的框架，使用 JIDL、`fetch_impl` 与 modlib；9 Pro 是旧的 AIOTJS 绑定。10 Pro 缺的只有一个 tun 驱动，同时比 9 Pro 多了一整套模块加载机制，理论上可以自行补上。

**纠正**：不是能力被砍，是某个驱动没有编进去，而补它的工具链反而更全。

**认知陷阱**：「缺一个功能」和「整体更弱」是两回事。先做逐项对比，再下「阉割」这种整体判断。

## 九条误判的共同结构

九条里有七条是同一个毛病：把「没观察到」当成「不存在」。

| 误判 | 没观察到的东西 | 错误推论 |
| --- | --- | --- |
| 一 | 已注册的 tun 接口 | 没有网络能力 |
| 二 | 中央目录 | 包不完整 |
| 三 | 函数名字符串 | 函数不存在 |
| 四 | PAN 代码 | 走的是 PAN，实际走 TUN |
| 五 | 端到端成功 | 能力被推翻 |
| 八 | 读取该字段的代码 | 字段是开关 |
| 九 | tun 驱动 | 整体被阉割 |

对应的纠正只有一句：否定性结论必须说明「找过了，而且检索方法覆盖所有可能位置」，否则只能写「暂未发现」。

剩下两条不属于同一结构：

| 误判 | 不同结构 | 教训 |
| --- | --- | --- |
| 六 | 目标错位，把手段当成了目标 | 先确认手段是否被排除 |
| 七 | 粒度错位，把静态链接当成了可搬运文件 | 先问移植的粒度 |

## 各结论的证据硬度

| 结论 | 硬度 | 状态 | 依据 |
| --- | --- | --- | --- |
| 10 Pro 有完整 TCP/IP 栈 | 高 | 已证实 | 大量符号与 NSH 命令 |
| 10 Pro 缺 `/dev/tun` 设备节点 | 高 | 已证实 | 手环日志 26 次 `ENOENT` |
| Miwear NET 是真实通路 | 高 | 已证实 | 两侧固件都有完整字符串与函数 |
| 手机侧代理已启动 | 高 | 已证实 | 手机日志 `started = true` |
| 10 Pro 有模块加载机制 | 高 | 已证实 | `insmod`、`modlib_*` 全部存在 |
| Canopus 能加载模块到 .043 | 中 | 推断 | 有 installer 代码，该固件标「待验证」 |
| `netdev_register @0xc1fc214` | 中 | 推断 | 单一来源，缺 `EVID-NET-001` |
| 写一个 tun 模块就能通 | 低 | 推断 | 推论，未实证 |

当前进度是：通路、机制、工具链都已经清楚，缺的是「写出来、装上去、跑通」这一步。
