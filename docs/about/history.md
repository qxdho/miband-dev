# 研究历程与误判

<StatusBadge status="sourced" verified="2026-10-25" />

九条误判中有七条源于同一个认知偏差，即将「没有观察到」等同于「不存在」。记录这些误判的主要价值在于，每条误判都指出了证据的边界；被推翻过的结论比未经检验的结论更能说明当前判断的可靠程度。

## 时间线

| 阶段 | 主张 | 结局 |
| --- | --- | --- |
| 一 | 「10 Pro 的快应用没有网络」 | 修正为「有网络栈、缺 tun 驱动」 |
| 二 | 「9 Pro 支持 fetch，10 Pro 不支持」 | 两者都有 fetch，差别不在代码 |
| 三 | 「需要第三方网桥才能上网」 | 用户否决：该方法正是待替代的对象 |
| 四 | 「官方 App 提供网络是幻想」 | 证伪：Miwear NET 真实存在 |
| 五 | 「10 Pro 根本没有通路」 | 证伪：通路存在，受阻于 `/dev/tun` |
| 六 | 「只能等厂商修」 | 证伪：Canopus 模块可以补 |
| 七 | 「要移植 9 Pro 的驱动文件」 | 修正：没有可移植的文件，需从源码编译模块 |

## 误判一：将 `getType: "none"` 判为无网络

严重度：高。状态：已推翻。

当时判断：探测脚本输出 `system.network.getType() === "none"`，据此认定手环没有网络接口。

当时依据：`getType` 返回 `none`，字面含义即没有网络类型。

为什么错：`uv_netstatus` 只枚举物理接口，类型表为：

```
wifi  wlan0  wlan1  cellsurf  cellular  bt-pan  bt-net  tun0  tun  eth0  ethernet
```

`tun` 确实在表内，但前提是有代码调用 `netdev_register` 将 tun 注册到表中。若未注册，表中即没有该接口，`getType` 自然返回 `none`。其正确含义是「没有已注册的网络接口」；「没有网络能力」属于另一层次的判断。前者说明缺少一次驱动注册动作，后者说明硬件或协议栈不存在。

纠正：`getType` 返回的是注册表快照，并不构成能力探测。判断能力需依据其他证据。

认知陷阱：接口的返回值反映当前注册状态，不反映潜在能力。API 报告「没有」时，可能仅表示尚未登记。

## 误判二：9 Pro 包中缺少应用镜像的判断

严重度：高。状态：已推翻。

当时判断：9 Pro 的 `firmware/9pro/fw9pro.bin` 中找不到 `vela_ap.bin`，只有 bootloader 与触摸固件，因此无法与 10 Pro 对比。

当时依据：`unzip -l` 与 Python `zipfile` 均无法打开该文件；文件尾缺少 `PK\x05\x06`（EOCD）；扫描 `PK\x03\x04` 命中 259 处，但没有一条能通过校验。

为什么错：该包只写本地文件头，不写中央目录。标准解析器均从 EOCD 入口查找，找不到即报告「不是 zip」，但数据本身是完好的。顺序扫描 `PK\x03\x04` 并逐条 inflate，可以完整解出 258 条，包括 `vela_ap.bin`，大小为 7,775,288 字节。

当时采用的校验标准是「能否组成合法的中央目录」，「inflate 是否成功」并未作为判据。判据选择不当，使一个完好的包被判定为损坏文件。

纠正：编写 `tools/zip_no_cd.js`，以逐条 inflate 成功作为判据。

认知陷阱：「标准工具打不开」与「文件损坏」属于两件事。需要先确认工具按何种规则查找入口，再确认数据是否存在。

## 误判三：字符串计数 0 等于函数不存在

严重度：高。状态：已推翻。

当时判断：10 Pro 的 `vela_ap.bin` 中 `netdev_register` 字符串计数为 0，而 9 Pro 为 1，因此判断 10 Pro 没有该接口，无法注册网络设备。

当时依据：字符串搜索是最直接的证据，计数为 0 即代表名称未出现在固件中。

为什么错：Canopus 的 3.101.043 target pack 明确记录：

```
netdev_register   entry 0xc1fc214   callable 0xc1fc215   int(void *, int)
```

函数与地址均存在，只是名称字符串被裁掉。固件为节省空间剥离符号名，仅保留地址表。字符串计数为 0 只说明名称未被保留，不能说明函数不存在。

纠正：字符串计数只能证明存在，不足以证明不存在。若要证明不存在，需检查符号表、重定位表，或反汇编目标地址以确认是否存在 `push {..., lr}` 一类的函数序言。

认知陷阱：否定性结论需要更强的证据。「已找到」构成充分证据，「未找到」只是弱证据。

## 误判四：使用蓝牙 PAN 的判断

严重度：中。状态：已推翻。

当时判断：手环通过蓝牙 PAN（BNEP）与手机组成 IP 网络。

当时依据：这是「蓝牙设备上网」最常见的做法；`bt-pan`、`bt-net` 也确实出现在网络类型表中。

为什么错：10 Pro 的 AP 中，`bt_sal_*` 函数仅有四类：`gatt_client_*`、`gatt_server_*`、`hid_device_*`、`spp_*`。PAN、BNEP、PANU、NAP 全部为 0，也没有 PPP，`pppd` 计数为 0。

实际机制为 Miwear NET，即一条运行于 BLE 之上的 TUN 通道。代码位于 `vendor/xiaomi/miwear/bluetooth/app/app_net.c`，日志字符串为：

```
[Miwear NET Connected]
failed to open /dev/tun: %d
ioctl TUNSETIFF failed: %d
Created Tun: %s
```

完整通路为：快应用 → libuv → TCP/IP 栈 → `/dev/tun` → `app_net.c` → BLE → 小米运动健康 → 互联网。

纠正：通路为 TUN over BLE，而非蓝牙 PAN。

认知陷阱：「常见做法」不构成证据。类型表中出现 `bt-pan` 只能说明代码支持该类型，不能说明实际使用了该类型。

## 误判五：「官方不支持 fetch」已被推翻的判断

严重度：中。状态：已推翻。

当时判断：`script.canUse('@system.fetch')` 返回 `true`，因此认为「10 Pro 不支持 fetch」的说法已被推翻。

当时依据：`canUse` 返回真，说明模块可用。

为什么错：`canUse` 只回答「该模块是否被编译进固件」，不回答「该模块能否工作」。在模块存在、接口可调用而底层没有网络出口的情况下，`canUse` 依然返回 `true`。正确的表述是「模块存在，但可用性未验证」；「不支持的说法已被推翻」则超出该证据所能支持的范围。

记录中曾出现一次自相矛盾：先判断不能据此断定可用，随后又表述为已被推翻。两种说法无法同时成立，后者将模块层的证据不适当地扩展到了产品层。

纠正：需要区分三个层次。

| 层次 | 要回答的问题 | 证据 | 状态 |
| --- | --- | --- | --- |
| 模块层 | 模块是否编译进固件 | `canUse` 返回 `true` | 已证实 |
| 权限层 | 调用是否被允许 | 调用能走到 DNS 解析，权限检查在更前面 | 已证实 |
| 产品层 | 是否有网络出口 | `/dev/tun` 不存在 | 已证实，结论为没有出口 |

认知陷阱：一个布尔值只能回答一个问题，不能为其他层次提供证据。

## 误判六：以网桥方案作为答案

严重度：中。状态：已推翻。

当时判断：编写一个 fetch 兼容层，将请求经 interconnect 转发到手机端接收器，由接收器发出 HTTP 请求。

为什么被否决：该方案技术上可行，但用户的目标是替代 interconnect，而该方案在机制上即为 interconnect，仅更换了 API 名称。用户否决时指出，其他网桥方案与之机制相同，而项目目标正是替代它。

纠正：目标在于「使用官方 App 的通道让 fetch 能用」，而非仅「让 fetch 能用」。前者可以使用任何传输方式，后者只能使用 Miwear NET，两者要求完全不同。

认知陷阱：需要先确认「手段」是否被排除在目标之外。若将「能用」视为目标、将「用官方通道」视为偏好，方向即会偏离。

## 误判七：对 9 Pro 驱动可移植的判断

严重度：中。状态：已推翻。

当时判断：9 Pro 有 tun 驱动，10 Pro 没有，将 9 Pro 的驱动迁移过去即可。

为什么错：9 Pro 的 tun 驱动以静态链接方式存在于 `vela_ap.bin` 中，并非可单独搬运的文件。9 Pro 的 `modlib`、`insmod` 字符串计数为 0，不存在模块机制，也没有可以拷贝的 `.ko`。

正确路径是使用 Canopus 的 SDK 重新编译一个 tun 驱动模块，加载到 10 Pro 上。10 Pro 具备完整的模块机制，`insmod`、`rmmod`、`lsmod`、`modlib_*` 全部存在。Canopus target pack 之所以关键，是因为它提供了编译所需的符号地址。

纠正：实际工作为重新编写模块，而非移植文件。

认知陷阱：「移植」需要先明确粒度。源码级、二进制级与模块级属于三种不同的操作。

## 误判八：将 `needNetwork` 判为网络开关

严重度：低。状态：已推翻。

当时判断：快应用 manifest 中有 `needNetwork` 字段，启用它可能即可联网。

为什么错：`needNetwork` 定义在 `vendor/oss_quickapp/include/quickapp.h:246`：

```c
bool needNetwork;   // APP是否依赖网络 默认false
```

该字段只是应用元数据，用于在应用商店或权限提示中显示「此应用需要网络」。固件中仅有一处引用，位于 `package.cpp` 中 apps.json 的序列化逻辑，没有任何代码依据它申请网络资源。

纠正：`needNetwork` 不触发任何网络动作。

认知陷阱：名称类似开关的字段通常只是标签。若要证明其为开关，需找到「读取该字段并改变行为」的代码。

## 误判九：将 10 Pro 视为阉割版本的判断

严重度：高。状态：已推翻。

当时判断：10 Pro 相比 9 Pro 削减了网络能力。

为什么错：对比两代 AP 的框架特征：

| 特征 | 10 Pro | 9 Pro |
| --- | --- | --- |
| JIDL feature 框架 | 21 处 | 0 |
| `fetch_impl` | 11 处 | 0 |
| 模块机制（`modlib`） | 16 处 | 0 |
| `tun%d` | 0 | 1 |
| `netdev_register`（字符串） | 0 | 1 |
| NSH 网络命令（`ifconfig`/`ifup`/`dns`/`dhcp`） | 有 | 未记录 |

10 Pro 是更新的框架，使用 JIDL、`fetch_impl` 与 modlib；9 Pro 则是旧的 AIOTJS 绑定。10 Pro 缺少的仅有一个 tun 驱动，同时比 9 Pro 多出一整套模块加载机制，理论上可以自行补上。

纠正：实际情况是某个驱动未被编入，而非整体能力被削减；补齐该驱动所需的工具链反而更为完整。

认知陷阱：「缺少一个功能」与「整体更弱」属于不同判断。应先做逐项对比，再作出「阉割」这类整体结论。

## 九条误判的共同结构

九条中有七条源于同一个问题：将「未观察到」等同于「不存在」。

| 误判 | 未观察到的对象 | 错误推论 |
| --- | --- | --- |
| 一 | 已注册的 tun 接口 | 没有网络能力 |
| 二 | 中央目录 | 包不完整 |
| 三 | 函数名字符串 | 函数不存在 |
| 四 | PAN 代码 | 走的是 PAN，实际走 TUN |
| 五 | 端到端成功 | 能力被推翻 |
| 八 | 读取该字段的代码 | 字段是开关 |
| 九 | tun 驱动 | 整体被阉割 |

对应的纠正可以概括为：否定性结论必须说明「已查找，且检索方法覆盖所有可能位置」，否则只能表述为「暂未发现」。

余下两条不属于同一结构：

| 误判 | 不同结构 | 教训 |
| --- | --- | --- |
| 六 | 目标错位，将手段当作目标 | 先确认手段是否被排除 |
| 七 | 粒度错位，将静态链接当作可搬运文件 | 先问移植的粒度 |

## 各结论的证据硬度

| 结论 | 硬度 | 状态 | 依据 |
| --- | --- | --- | --- |
| 10 Pro 有完整 TCP/IP 栈 | 高 | 已证实 | 大量符号与 NSH 命令 |
| 10 Pro 缺 `/dev/tun` 设备节点 | 高 | 已证实 | 手环日志 26 次 `ENOENT` |
| Miwear NET 是真实通路 | 高 | 已证实 | 两侧固件都有完整字符串与函数 |
| 手机侧代理已启动 | 高 | 已证实 | 手机日志 `started = true` |
| 10 Pro 有模块加载机制 | 高 | 已证实 | `insmod`、`modlib_*` 全部存在 |
| Canopus 能加载模块到 .043 | 中 | 推断 | 有 installer 代码，该固件标「待验证」 |
| `netdev_register @0xc1fc214` | 中 | 推断 | 单一来源，缺 `EVID-NET-001` |
| 写一个 tun 模块就能通 | 低 | 推断 | 推论，未实证 |

当前进度：通路、机制与工具链均已明确，尚缺「写出模块、安装到设备并完成验证」这一环节。
