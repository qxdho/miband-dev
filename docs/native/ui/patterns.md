# 原生开发模式：渲染、UI 与集成

<StatusBadge status="unverified" verified="2026-10-26" />

本页将原生模块开发中反复出现的问题抽象为若干模式，不针对任何具体项目。页面按画面来源划分为三条渲染路径，并分别讨论生命周期、固件接口、性能与检查清单。

## 一、三条渲染路径

| 路径 | 绘制主体 | 模块职责 | 典型代价 | 适用 |
| --- | --- | --- | --- | --- |
| A. 自绘帧缓冲 | 模块自身（CPU） | 逐像素写入 RGB565，按行或条带提交 | 算力开销最高，需自行管理同步与内存 | 3D、游戏、特殊视觉效果 |
| B. 系统文本控件 | 固件 UI | 仅发送文本、控件类型、布局与样式 | 控件表达力有限，绑定固件版本 | 聊天、工具、表单、纯文字界面 |
| C. 系统控件树（LVGL） | 固件 LVGL | 建立对象树、设置属性、接入事件 | 生命周期复杂，易出现 UAF 与错位 | 多页设置、列表、图标界面 |

选型顺序建议如下：

1. 若系统控件能够表达需求，选择 C；
2. 若仅需要文字与简单布局，选择 B，其成本最低；
3. 若画面无法由系统控件实现（体素地形、动画、逐像素效果），才选择 A。

## 二、自绘路径（A）

### 缓冲的来源

一块 480×336 的 RGB565 帧缓冲需要 `480×336×2 = 322,560` 字节。模块自身的 `.bss` 通常只有几 KB，无法容纳，因此缓冲一般由平台提供，模块通过「借用 / 归还」协议使用：

```
borrow()  → 拿到可写缓冲指针（或缓冲槽位）
写若干行
release() → 归还，交给显示侧
```

实现上常见的形式为两个指针配合一个状态机：`+0x560` / `+0x564` 存放前后缓冲地址，`+0x568` 存放状态（空闲 / 借出 / 已提交）。状态写入错误会导致撕裂或花屏。

### 行式、条带式渲染

整帧渲染完成后再提交的做法并不可取。更稳妥的做法是将一帧拆分为若干「步」：

```
begin()        准备相机、裁剪、雾与光照参数
step_rows()    渲染一段行，写入缓冲
step_rows()    …
submit()       提交这一段（脏矩形 / 命令列表）
```

该方式的优点是单次占用 CPU 的时间可控，掉帧表现为画面局部更新，不会造成整帧卡死，同时也便于与垂直同步对齐。

### 不使用深度缓冲的列式求交

体素画面可以使用「逐列光线投射」代替三角形光栅：

- 每一列沿相机方向发射一条射线；
- 沿射线执行 DDA，找到最近命中的方块面；
- 采样该面纹理，写入这一列像素。

这样每列仅保留最近命中，无需 `z-buffer`，可省去一整块与帧缓冲同尺寸的内存。其代价是每像素的浮点运算量更大。

### 软浮点的现实

若目标 ABI 为 soft-float（`.ARM.attributes` 中为 `EF_ARM_ABI_FLOAT_SOFT`，并导入 `__aeabi_fmul`、`__aeabi_fdiv` 等），每次乘除都需要经过 libgcc 函数调用，逐像素浮点运算开销较高。可用的优化手段如下：

- 帧内可预计算的量提前完成计算（相机矩阵、光照方向、列方向向量）；
- 远距离使用整数或定点近似，近距离再使用浮点运算；
- 按列进行粗判（区块可见性、面朝向、视距），先行排除后再精确计算；
- 水面、雾、天空等大面积区域采用低分辨率或查表方式处理。

### 提交与同步

「渲染完成」与「上屏」应分开处理：

- 每次提交一个脏矩形（或一段命令列表），硬件或驱动仅搬运变化区域；
- 使用 `present_ready` / `frame_released` 等回调控制节拍，避免在缓冲仍被显示侧读取时覆写；
- 命令列表通常有长度上限（例如单次 126 条），超出上限时需要拆批。

### 边界校验

自绘代码最容易在坐标上发生越界。至少需要校验以下条件：

```
0 <= x, y, w, h
x + w <= 480
y + h <= 336
offset + w*h*2 <= buffer_size
```

常量可以写成 `0x275FF`（`480*336 - 1`）和 `0x4EBFF`（`480*336*2 - 1`）的形式，用于上界判断。

## 三、系统控件树路径（C）

### 对象树结构

典型结构为三层：

```
page
 ├─ title（标题栏）
 └─ content（内容容器）
     ├─ row[0]（label / icon / picker）
     ├─ row[1]
     └─ …
```

页面仅负责「建树 / 拆树」，内容变化通过重建子树来表达。

### 四条生命周期规则

控件树的问题几乎都源于对象删除时机的选择。相关规则共四条：

1. 不在事件回调中删除当前对象

事件派发时框架正在遍历控件树，在回调中删除当前控件会使遍历器持有悬空指针（use-after-free），表现为花屏、重叠或死机。可行的做法是在回调中仅设置「待重画」标记，实际删除交由常驻定时器执行，该定时器不在事件派发上下文中运行。

```
on_click:
    request_render(page_id)   // 只置标记
    return

on_timer:
    if pending[page_id]:
        rebuild(page_id)      // 此时删除是安全的
```

2. 以重建代替就地刷新

就地刷新旧对象时，`align_to` 读取的仍是上一轮的几何信息（坐标、尺寸、父容器内边距），对齐结果会出现错误。可行的做法是先删除整棵内容子树，再执行与首次建页完全相同的 build 路径。

```
rebuild(page):
    if page.built:
        delete(page.content)
        delete(page.title)
    page.content = create_container()
    page.title   = create_title()
    build_rows(page)          // 与首次完全相同的路径
```

其代价是性能，收益是几何数据始终准确。

3. 槽位需要完整清理

页面通常使用固定容量数组缓存控件句柄。若删除对象后仅清理「本次用到的槽位」，其余旧句柄会处于悬空状态，下次重建复用时会访问已释放对象。清理时应写满整个数组，容量上限只保留单一常量来源。

4. 以全局前台页进行事件路由

同一套回调可能被多个页面共用。回调中应先判断当前前台页，再操作对应页面的控件：

```
fg_page = 0        // on_resume 时更新
on_row_event(slot):
    page = fg_page
    handle(page, slot)
```

## 四、系统文本控件路径（B）

该路径的模块代码通常仅包含「页面 + 文本 + 属性」：

- 控件通过属性编号进行配置，包括位置、尺寸、对齐、颜色、可见性与文本内容；
- 布局使用百分比而非像素，内部按 `/100` 换算；
- 页面生命周期由框架回调 `create` / `resume` / `pause` / `destroy` 驱动，模块只需注册一个描述符（函数指针表）；
- 中文输入依赖模块自带的拼音音节表与候选逻辑，字模由系统提供；
- 模块内不含字体数据，这是判断「渲染交由系统完成」的强信号。

## 五、与固件对接：硬编码地址的代价

原生模块无法导入固件符号，常见做法是将固件函数地址硬编码，再通过 `blx` 跳转执行：

```
movw r2, #0x2491
movt r2, #0x0458
bx   r2            // 调到固件里的某个 UI 函数
```

相关特征与风险如下：

- 符号表中没有 `UND` 符号，也没有对应库的符号名，但 `.text` 中出现 `0x04xxxxxx` 这类绝对地址；
- 地址与固件版本强绑定，更换固件后即会崩溃；
- 调试困难，崩溃现场通常只剩指向未知地址的 PC。

缓解措施如下：

1. 启动时探测固件版本与特征字节，不匹配时拒绝加载并回退；
2. 将地址集中到一张表中，按版本选择，避免散落在业务代码中；
3. 为关键调用封装一层，使失败可观测（日志、错误码），避免静默失败；
4. 采用灰度发布，先在小范围验证，再全量推送。

## 六、性能与内存预算

以 480×336 面板为例：

| 项 | 数值 | 说明 |
| --- | --- | --- |
| 单帧 RGB565 | 322,560 B | 320 KB 量级 |
| 双缓冲 | 645,120 B | 前后缓冲各一块 |
| 深度缓冲（若使用） | 322,560 B 起 | 能省则省 |
| 命令列表上限 | 约 126 条/批 | 超限需拆批 |

实践经验如下：

- 避免每帧动态分配，改用静态区或 arena；
- 将渲染与提交分离，把长任务切分为固定预算的步；
- 先行完成可见性裁剪，再进入逐像素循环；
- 在软浮点平台上，先测量再优化，优先减少函数调用次数。

## 七、开发检查清单

- [ ] 选型与需求相匹配（A/B/C 是否选择正确）
- [ ] 帧缓冲来源、所有权、双缓冲状态机是否闭环
- [ ] 所有坐标与偏移是否执行边界校验
- [ ] 渲染与提交是否分离，是否有防撕裂节拍
- [ ] 控件删除是否避开事件回调，是否走定时器
- [ ] 重建路径是否与首次建页一致
- [ ] 槽位数组是否每次完整清理
- [ ] 事件路由是否判断前台页
- [ ] 固件地址是否集中管理，是否有版本探测与回退
- [ ] 资源路径、权限与掉电保存是否经过验证
- [ ] 崩溃是否有可观测输出（日志 / 错误码）

## 八、速查

| 问题 | 优先排查 |
| --- | --- |
| 花屏、局部乱码 | 双缓冲状态机、事件回调中删对象、槽位未清满 |
| 错位、重叠、空白 | 就地刷新导致脏几何、布局百分比换算 |
| 卡顿、掉帧 | 整帧一次渲染、软浮点热点、每帧分配 |
| 更换固件即崩溃 | 硬编码地址未探测、结构体偏移变化 |
| 死机无输出 | 内核态越界、空指针、未处理错误码 |
