# 附录 · 研究历程与误判

## 本文讲什么

这个项目走过不少弯路。把误判记下来不是为了检讨，而是因为**每一条误判都对应一个具体的认知陷阱**，而正文的结论正是从这些陷阱里爬出来之后才立住的。

**读法**：如果你只想看结论，看[正文](README.md)；如果你想判断某个结论有多可靠，看这篇——**被推翻过的结论比没被检验过的结论更可信**。

## 时间线概要

| 阶段 | 主张 | 结局 |
|---|---|---|
| 一 | "10 Pro 的快应用没有网络" | 后被修正为"有网络栈、缺 tun 驱动" |

| 三 | "需要第三方网桥才能上网" | 用户否决：那正是要替代的东西 |

## 误判一：把 `getType: "none"` 当成"没有网络"

**当时的说法**：探测脚本输出 `system.network.getType() === "none"`，据此判断手环没有网络接口。

**当时依据**：`getType` 返回 `none`，字面意思就是没有网络类型。

**为什么错**：

`uv_netstatus` 只枚举**物理接口**，它的类型表是：

```
wifi  wlan0  wlan1  cellsurf  cellular  bt-pan  bt-net  tun0  tun  eth0  ethernet
```

`tun` 确实在表里——但前提是**有人调用 `netdev_register` 把 tun 注册进去**。没注册，表里就没有这个接口，`getType` 自然返回 `none`。

所以 `none` 的正确含义是"**没有已注册的网络接口**"，而不是"没有网络能力"。这两个意思差得很远：前者说明缺一个驱动注册动作，后者说明硬件/协议栈不存在。

**纠正**：`getType` 是"注册表快照"，不是"能力探测"。判能力要看别的东西。

**教训**：**接口的返回值反映的是"当前注册状态"，不是"潜在能力"。** 一个 API 报"没有"，可能只是"还没人登记"。

## 误判二：9 Pro 包里没有应用镜像

**当时的说法**：9 Pro 的 `firmware/9pro/fw9pro.bin` 里找不到 `vela_ap.bin`，只有 bootloader 和触摸固件，所以无法对比。

**当时依据**：用 `unzip -l` 和 Python `zipfile` 都打不开；文件尾没有 `PK\x05\x06`（EOCD）；扫 `PK\x03\x04` 命中 259 处但"没有一个能通过校验"。

**为什么错**：

那个包是**只写本地文件头、不写中央目录**的 zip。所有标准解析器都从 EOCD 入口，找不到就报"不是 zip"。但数据完好——顺序扫 `PK\x03\x04`，逐条 inflate，能完整解出 **258 条**，包括 `vela_ap.bin`（7,775,288 字节）。

我当时的"校验"用的是"是否能组成合法的中央目录"，而不是"inflate 是否成功"。判据选错了。

**纠正**：写了 `tools/zip_no_cd.js`，以"逐条 inflate 成功"为判据。

**教训**：**"标准工具打不开"和"文件坏了"是两件事。** 先问"它按什么规则找入口"，再问"数据在不在"。

## 误判三：字符串计数 0 = 函数不存在

**当时的说法**：10 Pro 的 `vela_ap.bin` 里 `netdev_register` 字符串计数为 0，而 9 Pro 为 1，所以 10 Pro 没有这个接口，无法注册网络设备。

**当时依据**：字符串搜索是最直接的证据。

**为什么错**：

Canopus 的 3.101.043 target pack 里明确记录：

```
netdev_register   entry 0xc1fc214   callable 0xc1fc215   int(void *, int)
```

函数在，地址在，只是**名字字符串被裁掉了**。固件为了省空间剥掉了符号名，只保留地址表。

**纠正**：字符串计数只能证明"存在"，不能证明"不存在"。要证明不存在，得查符号表/重定位表，或反汇编目标地址看是不是有效函数序言（`push {..., lr}` 之类）。

**教训**：**否定性结论需要更强的证据。** "找到了"是充分证据，"没找到"只是弱证据。

## 误判四：以为走的是蓝牙 PAN

**当时的说法**：手环通过蓝牙 PAN（BNEP）和手机组成 IP 网络。

**当时依据**：这是"蓝牙设备上网"最常见的做法；而且 `bt-pan`、`bt-net` 出现在网络类型表里。

**为什么错**：

10 Pro 的 AP 里，`bt_sal_*` 函数只有四类：`gatt_client_*`、`gatt_server_*`、`hid_device_*`、`spp_*`。**PAN/BNEP/PANU/NAP 全部为 0**。也没有 PPP（`pppd`=0）。

真正的机制是 **Miwear NET：一条跑在 BLE 上的 TUN 通道**。代码在 `vendor/xiaomi/miwear/bluetooth/app/app_net.c`，日志字符串是：

```
[Miwear NET Connected]
failed to open /dev/tun: %d
ioctl TUNSETIFF failed: %d
Created Tun: %s
```

**纠正**：通路是 `快应用 → libuv → TCP/IP 栈 → /dev/tun → app_net.c → BLE → 小米运动健康 → 互联网`。

**教训**：**"常见做法"不是证据。** 类型表里有 `bt-pan` 只说明代码支持这种类型，不说明实际用的是它。

## 误判五：以为"官方不支持 fetch"已被推翻

**当时的说法**：`script.canUse('@system.fetch')` 返回 `true`，所以"10 Pro 不支持 fetch"的说法被推翻了。

**当时依据**：`canUse` 返回真。

**为什么错**：

`canUse` 只回答"**这个模块编译进固件了吗**"，不回答"**它能不能工作**"。模块在、接口能调、但底层没有网络出口——`canUse` 依然返回 `true`。

所以当时正确的表述应该是："模块存在，但可用性未验证"，而不是"不支持的说法被推翻"。我一开始说对了（"不能据此断定可用"），后来又自己说成了"被推翻"，这是一个自我矛盾。

**纠正**：区分三个层次——

| 层次 | 问题 | 证据 |
|---|---|---|
| 模块层 | 编译进去了吗 | `canUse` = true ✅ |
| 权限层 | 允许调用吗 | 调用能走到 DNS 解析 ✅（权限在更前面） |
| 产品层 | 有网络出口吗 | ❌ 没有（`/dev/tun` 不存在） |

**教训**：**一个布尔值只能回答一个问题。** 别让它替别的层次作证。

## 误判六：拿网桥方案当答案

**当时的说法**：写一个 fetch 兼容层，把请求经 interconnect 转发到手机端接收器，由接收器发 HTTP。

**为什么不算误判，但被否决**：

技术上可行。但用户的目的是**替代 interconnect**，而这个方案的本质就是 interconnect——只是换了个 API 名字。用户原话：

> 可是我要用小米运动健康官方应用 其他的网桥方案不就是你现在这个方案吗 我要代替它啊

**纠正**：目标不是"让 fetch 能用"，而是"**用官方 App 的通道让 fetch 能用**"。这两者要求完全不同：前者可以用任何传输，后者只能用 Miwear NET。

**教训**：**先确认"手段"是不是被排除在目标之外。** 我一开始把"能用"当目标，把"用官方通道"当偏好，方向就偏了。

## 误判七：以为要移植 9 Pro 的驱动

**当时的说法**：9 Pro 有 tun 驱动，10 Pro 没有，把 9 Pro 的驱动搬过去就行。

**为什么错**：

9 Pro 的 tun 驱动**不是一个可搬运的文件**——它静态链接在 `vela_ap.bin` 里（9 Pro 的 `modlib`/`insmod` 字符串为 0，根本没有模块机制）。没有 `.ko` 可以拷。

真正的路径是：**用 Canopus 的 SDK 重新编译一个 tun 驱动模块**，加载到 10 Pro 上。10 Pro 恰好有完整的模块机制（`insmod`/`rmmod`/`lsmod`/`modlib_*` 全在）。

**纠正**：不是"移植文件"，是"重写模块"。这也解释了为什么 Canopus 的 target pack 对本项目如此关键——它提供了编译所需的符号地址。

**教训**：**"移植"要先问移植的粒度。** 源码级、二进制级、模块级是三件不同的事。

## 误判八：把 `needNetwork` 当成网络开关

**当时的说法**：快应用 manifest 里有 `needNetwork` 字段，打开它可能就能联网。

**为什么错**：

`needNetwork` 定义在 `vendor/oss_quickapp/include/quickapp.h:246`：

```c
bool needNetwork;   // APP是否依赖网络 默认false
```

它只是**应用元数据**，用来在应用商店/权限提示里显示"此应用需要网络"。固件里只有一处引用（`package.cpp` 里 apps.json 的序列化），没有任何代码根据它去申请网络资源。

**纠正**：它不触发任何网络动作。

**教训**：**名字像开关的字段，多半只是标签。** 要证明它是开关，得找到"读它并改变行为"的代码。

## 误判九：以为 10 Pro 是"阉割版"

**当时的说法**：10 Pro 相比 9 Pro 砍掉了网络能力。

**为什么错**：

对比两代 AP 的框架特征：

| 特征 | 10 Pro | 9 Pro |
|---|---|---|
| JIDL feature 框架 | 21 处 | 0 |
| `fetch_impl` | 11 处 | 0 |
| 模块机制（`modlib`） | 16 处 | 0 |
| `tun%d` | **0** | 1 |
| `netdev_register`（字符串） | 0 | 1 |
| NSH 网络命令（`ifconfig`/`ifup`/`dns`/`dhcp`） | 有 | — |

10 Pro 是**更新的框架**（JIDL + fetch_impl + modlib），9 Pro 是旧的 AIOTJS 绑定。10 Pro 缺的恰恰只是**一个 tun 驱动**——而它比 9 Pro 多了一整套模块加载机制，理论上可以自己补上。

**纠正**：不是"能力被砍"，是"某个驱动没编进去，但补它的工具链反而更全"。

**教训**：**"缺一个功能"和"整体更弱"是两回事。** 先做逐项对比，再下"阉割"这种整体判断。

## 这些误判的共同结构

回头看，九条里有七条是同一个毛病：**把"没观察到"当成"不存在"**。

| 误判 | 没观察到的东西 | 错误推论 |
|---|---|---|
| 一 | 已注册的 tun 接口 | 没有网络能力 |
| 二 | 中央目录 | 包不完整 |
| 三 | 函数名字符串 | 函数不存在 |
| 四 | PAN 代码 | 走的是 PAN（其实走 TUN） |
| 五 | 端到端成功 | 能力被推翻 |
| 八 | 读取该字段的代码 | 字段是开关 |
| 九 | tun 驱动 | 整体被阉割 |

对应的纠正只有一句：**否定性结论必须给出"我找过了，找的方法能覆盖所有可能位置"的证明**，否则只能说"暂未发现"。

## 哪些结论现在比较硬

| 结论 | 硬度 | 依据 |
|---|---|---|
| 10 Pro 有完整 TCP/IP 栈 | 🟢 硬 | 大量符号 + NSH 命令 |
| 10 Pro 缺 `/dev/tun` 设备节点 | 🟢 硬 | 手环日志 26 次 `ENOENT` |
| Miwear NET 是真实通路 | 🟢 硬 | 两侧固件都有完整字符串与函数 |
| 手机侧代理已启动 | 🟢 硬 | 手机日志 `started = true` |
| 10 Pro 有模块加载机制 | 🟢 硬 | `insmod`/`modlib_*` 全在 |
| Canopus 能加载模块到 .043 | 🟡 中 | 有 installer 代码，但该固件标"待验证" |
| `netdev_register @0xc1fc214` | 🟡 中 | 单一来源，缺 `EVID-NET-001` |
| 写个 tun 模块就能通 | 🟠 弱 | 推论，未实证 |

**这就是当前的真实进度**：通路、机制、工具链都清楚了，缺的是"写出来、装上去、跑通"这一步。
