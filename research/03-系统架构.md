# 03 · 系统架构

## 本文讲什么

10 Pro 上跑的是什么系统、分成几层、内核里到底编进去了哪些东西。这是判断"某个能力是缺代码还是缺配置"的地基——很多结论只有放在这一层看才成立。

**结论**：系统是 NuttX + Vela 应用框架。**内核的网络用户态工具非常完整**（`ifconfig` 连 `dns`、`dhcp`、`gw` 参数都支持），TCP/IP 协议栈也在，唯独缺**创建 `/dev/tun` 并把它注册成网卡的那段驱动代码**（注册 API 本身是存在的，见下），以及 DNS 解析器。`modlib` 模块子系统存在，是 10 Pro 相对 9 Pro 最大的架构优势。

## 分层

```
┌─────────────────────────────────────────────┐
│  快应用 (QuickJS)  ← JSLab / 计算器 / 日程…  │
├─────────────────────────────────────────────┤
│  Vela 应用框架（feature 框架 + JIDL 绑定）   │
├─────────────────────────────────────────────┤
│  系统服务：lvgl / libuv / miwear / app_net   │
├─────────────────────────────────────────────┤
│  NuttX 内核：调度、VFS、TCP/IP、modlib       │
├─────────────────────────────────────────────┤
│  BES 芯片：BL → BL2 → AP                     │
└─────────────────────────────────────────────┘
```

| 层 | 证据 |
|---|---|
| QuickJS | 固件里有完整 Lua/JS 运行时字符串表（`collectgarbage`、`dofile`、`getmetatable`…） |
| Vela 框架 | `jidl_feature`（21 处）、`fetch_impl`（11 处） |
| libuv | `uv_networkcache.c`、`uv_netstatus`、`uv_miwear.c` |
| NuttX | `nuttx/libs/libc/modlib/*`、`nuttx/net/tcp/*`、NSH 命令表 |
| BES | `ZZ~` 容器、`vela_bl.bin` / `vela_bl2.bin` / `vela_ap.bin` 三段式 |

## 内核

### 版本被抹掉了

固件里 `NuttX` 只出现 2 次，`nuttx-` 出现 0 次，版本串是 `NuttX 0.0.0`——发行版把版本号抹成了占位符。所以无法直接对照上游版本，只能按**存在哪些源文件路径**反推配置。

### 内存布局

| 区域 | 地址 | 说明 |
|---|---|---|
| 代码别名 | `0x0C000000` | 镜像映射，指令取指 |
| 数据别名 | `0x2C0C0000` | 同一份字节的第二个映射 |
| 初始栈顶 | `0x28DE8024` | 向量表第 0 项 |
| 内核堆 | 由 NuttX 管理 | 模块加载也从这里分配 |

双映射的推导与验证见 [01 篇](01-固件研究-10Pro.md#地址换算规则关键)。

### NSH 命令行

10 Pro 编进了一张完整的 NSH 命令表，位置在 `vela_ap.bin` 偏移 `0xa6d800`–`0xa6da00` 附近。每个条目是「命令名 + 帮助串」紧挨着排列：

```
... mv\0\0<old-path> <new-path>\0\0\0mw\0\0<hex-address>[=<hex-value>]...
... nslookup\0\0\0\0<host-name>\0pidof\0\0\0pmconfig\0\0\0\0[stay|relax]...
... hexdump\0<file or device>\0\0\0\0ifconfig\0\0\0\0[interface [mtu <len>]|
    [address_family] [[add|del] <ip-address>|dhcp]] [dr|gw|gateway ...
    ... <net-mask>|prefixlen <len>] [dns <dns-address>] [hw <hw-mac>]\0\0\0ifdown\0\0<interface>\0
    ifup\0\0\0\0insmod\0\0<file-path> <module-name>\0\0\0kill\0\0\0\0[-<signal>] <pid>\0\0
    pkill\0\0\0[-<signal>] <name>\0\0lose...
```

从这张表本身就能读出很多信息：

| 命令 | 帮助串 | 意义 |
|---|---|---|
| `ifconfig` | `[interface [mtu <len>]\|[address_family] [[add\|del] <ip-address>\|dhcp]] [dr\|gw\|gateway <net-mask>\|prefixlen <len>] [dns <dns-address>] [hw <hw-mac>]` | **完整版**，能配 IP、掩码、网关、DNS、MAC、DHCP |
| `ifup` / `ifdown` | `<interface>` | 接口启停 |
| `insmod` | `<file-path> <module-name>` | **模块加载可用** |
| `rmmod` / `lsmod` | — | 模块卸载 / 列表 |
| `nslookup` | `<host-name>` | DNS 查询客户端在 |
| `netstat` / `route` / `arp` | — | 网络诊断套件在 |
| `losetup` | — | 回环设备，可从文件挂镜像 |
| `ps` / `free` / `df` / `mount` / `md5` | — | 常规运维 |

**这张表是"网络用户态齐备"的直接证据。** 一旦有了网卡驱动，`ifconfig tun0 ...` + `ifup tun0` 就能把它拉起来，不需要再补任何用户态代码。

> ⚠️ 一个容易误判的点：`wget` 在固件里只出现 1 次，但那一次在 Lua 基础库的字符串表里（`collectgarbage`、`dofile`、`getmetatable`⋯⋯旁边），**不是 NSH 命令**。不要据此认为板子带 wget。

### TCP/IP 协议栈

协议栈主体是完整的：

| 文件路径（固件内嵌的调试串） | 状态 |
|---|---|
| `nuttx/net/tcp/tcp_connect.c` | ✅ 在 |
| `nuttx/net/tcp/tcp_input.c` | ✅ 在 |
| `nuttx/net/tcp/tcp_send_unbuffered.c` | ✅ 在 |
| `nuttx/net/socket/connect.c` | ✅ 在 |
| `nuttx/net/socket/sendmsg.c` | ✅ 在 |
| `nuttx/net/socket/recvmsg.c` | ✅ 在 |

这意味着 `socket()`、`connect()`、`send()`、`recv()` 全部可用。实测中 `connect()` 到裸 IP 返回 `code:7`（`Couldn't connect to server`，约 59 ms）而不是 `ENETUNREACH` 卡住，说明是**没有路由表项**导致的快速失败，协议栈本身在工作。

### 缺的是什么

| 符号 / 串 | 存在 | 后果 |
|---|---|---|
| `netdev_register` | ❌ 0 次（**只是名字**） | 函数本体存在：`0xc1fc214`，IDA 精确恢复，见 [06 篇](附录-研究历程与误判.md#误判三字符串计数-0-函数不存在) |
| `tun%d` | ❌ 0 次 | 没有 TUN 设备的命名/创建 |
| `lib_getaddrinfo.c` | ❌ 不在 `netdb/` 的 6 个源文件里 | 域名解析不可用 |
| `nuttx/net/dns/` | ❌ 0 | DNS 客户端库未编入 |
| `dns_add_nameserver` / `resolv.conf` / `ipv4_dns` | ❌ 0 | 无域名服务器配置机制 |
| `SIOCGIFCONF` | ❌ 0 | 无法枚举接口 |

`/nuttx/libs/libc/netdb/` 目录只列出了 6 个源文件路径，**`lib_getaddrinfo.c` 不在其中**——这是"域名解析根本编不进来"的硬证据，也解释了实测中所有域名请求都以 `Couldn't resolve host name` 失败。

> ❓ **一个矛盾点**：NSH 命令表里有 `nslookup`，但 DNS 客户端库看起来没编进来。可能是 applet 保留了名字而实现被裁掉，也可能 DNS 代码在别处（如 `netutils`）而没留源文件路径串。这一点没有闭环，如果要走"补 DNS"的路线，得先验证 `nslookup` 是否真能跑。

## modlib：10 Pro 的独有能力

| 证据 | 10 Pro | 9 Pro |
|---|---|---|
| `nuttx/libs/libc/modlib/` 源文件路径 | ✅ 多个 | ❌ 0 |
| `modlib` 字符串 | 16 | 0 |
| `insmod` | 1 | 0 |
| `rmmod` / `lsmod` | 1 / 1 | 0 / 0 |
| `modlib_symtab` | 1 | 0 |

这是**整个研究里最重要的一个差异**：9 Pro 的一切都是静态编进 `vela_ap.bin` 的，想加功能只能改固件重刷（被签名挡住）；10 Pro 留了运行时加载模块的口子。

细节（模块格式、符号解析、加载链路）见 [06 篇](06-内核模块系统.md)。

## 分区与文件系统

### 存储分区

| 节点 | 内容 | 写入者 |
|---|---|---|
| `/dev/bl` | 一级引导 | 工厂 |
| `/dev/bl2` | 二级引导 | `ota.sh` |
| `/dev/ap` | 应用处理器镜像 | `ota.sh` |
| `/dev/resource` | 资源分区（171 MB） | `ota.sh` |
| `/dev/ota` | OTA 暂存 | 升级时 |
| `/dev/ota_data` | OTA 元数据 | 升级时 |
| `/dev/factory` | 工厂数据 | 工厂 |
| `/dev/efuse` / `/dev/otp` | 一次性可编程区 | 工厂 |

### 运行时文件系统

| 路径 | 内容 |
|---|---|
| `/data/` | 用户数据：`apps.json`、已装快应用、日志 |
| `/data/offlinelog/` | 离线日志 `log1.gz` … `log6.gz`（每个解压后 2 MB） |
| `/data/dfx/note/` | 诊断事件 `*.ev.gz` |
| `/system/` | 系统资源：`watchface/<id>/resource.bin` |
| `/ota/` | 升级包暂存 |
| `/dev/` | 设备节点 |

`/data/apps.json` 是快应用的注册表，字段包括 `names`、`minAPILevel`、`minPlatformVersion`、`standalone`、`needNetwork`、`installedTimestamp`（序列化代码在 `package.cpp`）。

### `/dev` 节点

9 Pro 的 bring-up 列表（10 Pro 结构相同）：

```
/dev/urandom  /dev/loop   /dev/ptmx     /dev/utouch
/dev/ubutton  /dev/ukeyboard             /dev/usensor
```

**注意这里没有 `/dev/tun` 的创建代码**——9 Pro 的 `/dev/tun` 是在 `nx_bringup` 里和 `eth%d`、`tun%d` 一起注册的（见 [02 篇](02-固件研究-9Pro.md#一个容易搞错的地方)），10 Pro 对应的那行被裁掉了。

## 与 9 Pro 的架构对比

| 维度 | 10 Pro | 9 Pro |
|---|---|---|
| 应用框架 | 新一代 feature 框架（`jidl_feature` 21） | 上一代（0） |
| fetch 实现 | `fetch_impl` 独立模块（11） | 内联在 AIOTJS 绑定里 |
| 模块加载 | ✅ `modlib` + `insmod` | ❌ 无 |
| TUN 驱动 | ❌ 未编入 | ✅ 静态编入 |
| 网络用户态 | ✅ 完整 NSH 套件 | ✅ |
| 资源组织 | 单个 171 MB `vela_resource.bin` | 按功能拆成多个 `.res` |
| 固件签名 | ✅ ZIP + CERT | ❓ 未验证 |

一句话概括：**9 Pro 是"一切都编好"，10 Pro 是"框架留了口子但驱动没装"**。这恰好是为什么 10 Pro 反而有救——只要有办法把驱动塞进去。
