# 05 · 网络通路

## 本文讲什么

一个 `fetch` 请求在手环内部要经过哪些层才能到达互联网，每一层在 10 Pro 上是否健全，以及**断点究竟在哪一层**。这一篇推翻了本文档早期的一个错误结论（"手环完全没有网络出口"），结论以本篇为准。

**结论**：通路在设计上是完整的，手机侧甚至已经成功启动了代理。断点在**手环侧的一个设备节点**：`/dev/tun` 不存在，导致隧道客户端 `net_tun_open()` 以 `errno 2 (ENOENT)` 失败。这不是配置问题，是驱动没编进固件。

## 完整链路

```
┌─ 手环 ───────────────────────────────────────────────┐
│                                                       │
│  快应用 JS                                            │
│    ↓  fetch.fetch({url})                              │
│  Vela 绑定层 / fetch_impl                             │
│    ↓                                                  │
│  libuv  (uv_miwear.c, uv_netstatus)                   │
│    ↓                                                  │
│  NuttX TCP/IP 栈 (net/tcp/*, net/socket/*)            │
│    ↓  查路由表 → 找出口网卡                            │
│  ┌─────────────────────────────────┐                  │
│  │  ✗ 没有已注册的网卡              │  ← 断点在这里    │
│  └─────────────────────────────────┘                  │
│    ↓  （本该是 /dev/tun）                              │
│  app_net.c 隧道客户端                                 │
│    ↓  BLE GATT                                        │
└───────────────────────────────────────────────────────┘
     ↓
┌─ 手机 ────────────────────────────────────────────────┐
│  小米运动健康                                          │
│  NetProxyManager → NetProxyComponent                  │
│    ↓  (JNI)                                           │
│  Android 网络 → 互联网                                 │
└───────────────────────────────────────────────────────┘
```

链路的两端都有代码，**中间那一段（网卡注册）在 10 Pro 上不存在**。

## 逐层证据

### 1. 应用层 → libuv

固件里有 libuv 的网络状态实现：

```
../../frameworks/system/utils/uv/src/uv_miwear.c
../../frameworks/system/utils/uv/src/uv_networkcache.c
```

以及它的日志格式串：

```
["uv_netstatus":%d]uv_ifstatus_isup: name: %s, flags: %d
["uv_netstatus":%d]uv_netstatus_gettype: name: %s, status :%s
```

`uv_miwear.c` 的存在说明 libuv 在这一层就接上了小米自己的传输栈，而不是走通用 socket 抽象。

### 2. TCP/IP 栈

完整的 NuttX 网络栈（见 [03 篇](03-系统架构.md#tcpip-协议栈)）。实测中 `connect()` 到裸 IP 在 59 ms 内失败，说明协议栈在跑，只是**没有出口设备**。

### 3. `/dev/tun`

| 证据 | 10 Pro | 9 Pro |
|---|---:|---:|
| `/dev/tun` 字符串 | 2（都是 `app_net.c` 的日志串） | 2（一个是 bring-up 注册，一个是日志串） |
| `TUNSETIFF` | 1 | 1 |
| `tun%d` | **0** | **1** |
| `netdev_register` | **0** | **1** |

10 Pro 的 `app_net.c` **会去打开 `/dev/tun`**，但**没有任何代码创建它**。

### 4. `app_net.c`：隧道客户端

固件里保留了完整的格式串，足以还原这个模块的功能：

```
netif %s %s
Miwear NET Connected
Miwear NET Disconnected
[Miwear NET][%s] %s: failed to open /dev/tun: %d
[Miwear NET][%s] %s: ioctl TUNSETIFF failed: %d
[Miwear NET][%s] %s: Created Tun: %s
ioctl SIOCGIFMTU failed: %d
poll events:%d status:%d
poll disconnected
invalid tun fd
write fail:%d errno:%d
Can't open socket: %d
```

对应的函数名（同样以字符串形式存在）：

| 函数 | 职责 |
|---|---|
| `net_tun_open` | 打开 `/dev/tun`，`ioctl(TUNSETIFF)` 建接口 |
| `net_tun_close` | 关闭 |
| `net_tun_poll_data` | 轮询收包 |
| `net_get_tun_packet_size` | 取包长 |
| `net_uv_poll_start` | 把 fd 挂到 libuv 事件循环 |
| `netif_switch` | 切换接口 up/down |
| `net_trans` | 传输 |
| `net_sockif` | socket 接口 |
| `net_reconnect` | 重连 |
| `app_net_receive` | BLE 收到数据 → 写 tun |
| `app_net_connect_state_update` | 连接状态回调 |
| `remote_net_state_switch` | **手机侧下发的开关**（10 Pro 独有） |

看这个函数清单就知道：**这是一个写完整的 TUN-over-BLE 客户端**，不是半成品。它唯一的前提是 `/dev/tun` 存在。

### 5. 手机侧：代理已经起来了

小米运动健康日志（`XiaomiFit.device.log`，UTC+8）：

```
NetProxyComponent|onConnectSuccess() called with: net proxy did = 2239055857
NetProxyComponent|onConnectSuccess: support net proxy = true
NetProxyManager|start() called, jniContext = 503260182864, started = true
DeviceBasicStatusDataHandler|addHandler ... NetProxyComponent$upstreamHandleData$1
```

| 日志 | 含义 |
|---|---|
| `support net proxy = true` | 手机认为这台手环**支持**网络代理 |
| `started = true` + 非零 `jniContext` | 代理对象真的建起来了 |
| `net proxy did = 2239055857` | 只对 10 Pro 建，从未对 9 Pro 建过 |
| `upstreamHandleData` | 上行数据通道已注册 |

**手机侧没有任何问题。**

#### 一个容易看漏的细节：第一次 `start()` 是空转

```
19:08:58.492  NetProxyManager|start() called, jniContext = 0, started = false
19:09:27      ← 探针在这个时间点跑，代理还没真正启动
19:09:46.021  NetProxyManager|start() called, jniContext = 503260182864, started = true
19:09:53.938  onDeviceLost
```

第一次 `start()` 带着 `jniContext = 0`，是空转；第二次才拿到真实上下文。而**探针恰好跑在两次之间**，所以那一轮实测的失败不能完全归因于驱动缺失——不过后来的探针（在代理启动后）仍然是 `code 7`，所以结论不变。

更值得注意的是最后一行：**真实代理启动后 7.9 秒，BLE 连接就断了**。重连时 `errorCode = 2011/2012`。这个"一开代理就掉线"的现象在整份日志里反复出现，是另一个独立问题（见本文末"未决"）。

### 6. 手环侧：决定性的日志

`/data/offlinelog/log*.gz` 里，从 10/16 15:36 到 10/17 11:44，**26 次，无一例外**：

```
[10/17 11:19:05] [30] [ ERROR] [ap] [bt] net_tun_open: failed to open /dev/tun: 2
[10/17 11:19:05] [30] [ ERROR] [ap] [bt] app_net_connect_state_update: tun open fail
```

`errno 2 = ENOENT`，即**文件不存在**。

- 不是权限问题（那会是 `EACCES = 13`）
- 不是设备忙（`EBUSY = 16`）
- 不是 ioctl 失败（那会打 `ioctl TUNSETIFF failed`）
- 是**这个设备节点压根没有**

而且它发生在 `app_net_connect_state_update` 里——即"连接状态更新"回调中。也就是说：**手机连上了 → 手环收到通知 → 手环尝试开 tun → 失败**。链路的前半段是通的。

> 注意日志时间戳是 **UTC**，手机日志是 **UTC+8**。对齐时要减 8 小时，否则会得出"手环没反应"的错误结论。

## `remote_net_state_switch`：谁控制开关

10 Pro 有、9 Pro 没有的一个符号。字符串在文件偏移 `0xc8b638`，对应数据地址 `0x2cd4b638`。

按 [01 篇](01-固件研究-10Pro.md#地址换算规则关键)的规则找引用：

| 搜索基准 | 命中 |
|---|---|
| 代码别名 `0x0C000000` | 0 处 |
| 数据别名 `0x2C0C0000` | **1 处 @ 文件 `0x651730`** |

反汇编 `0x0c651730` 附近，发现它落在一个**字面量池**里，周围的 32 位字是：

```
0x20126c88, 0x20126c8a, 0x20126c89,
"up", "bt-net", "remote_net_state_switch", "bt",
0x2cc15e84, "down"
```

同一段代码里的另一处字面量池（`0x6515ac` 附近）是：

```
"app_net_connect_state_update", "bt", "/dev/tun", "up",
"netif_switch", "net_tun_open", "bt-net", "net_get_tun_packet_size"
```

### 这说明什么

1. 这两个池里的字符串**只是日志元数据**（"模块名/函数名"标签），不是调度表。
2. `remote_net_state_switch` 在**整个固件里没有任何代码通过它做分派**——没有 PC 相对的加载器，没有跳转表。
3. 所以真正的 topic id 在别处（可能是数字常量），字符串只用于打日志。

### 推论

**开关的决定权在手机侧。** 手环侧没有找到任何本地触发点。这符合协议设计：手环不知道自己该不该上网，得手机告诉它。

⚠️ 这一点是**推断**，因为没能定位到实际的 message handler。如果将来要自己发这个 topic，得先在手机 App 里抓包确认 topic id 和 payload 格式（payload 看着是 `"up"` / `"down"` 字符串）。

## 为什么 `getType` 不能当判据

`system.network.getType()` 在实测中返回 `"none"`。这个东西很容易被误读成"设备没有网络"。

### 它的实现

```
["uv_netstatus":%d]uv_netstatus_gettype: name: %s, status :%s
```

配套的类型名表（固件里连在一起）：

```
wifi  wlan0  wlan1  cellsurf  cellular  bt-pan  bt-net  tun0  tun  eth0  ethernet
```

### 正确的读法

`getType()` = "遍历已注册的网络设备，把名字映射成上表的某个类型；一个都没匹配上就返回 `none`"。

所以：

| 你看到的 | 真实含义 |
|---|---|
| `getType() === 'none'` | **内核里没有已注册的网络设备** |
| 有 tun 设备时会返回什么 | 表里有 `tun0` / `tun`，所以会返回 `"tun"`（推断） |

**注意 `tun` 就在这张表里。** 所以早期"TUN 不在 getType 的类型表里，所以 getType 永远是 none"的说法是**不准确的**——表里有它。真正的原因是：**设备根本没注册，表里有什么都没用**。

一句话：`getType` 不是独立证据，它只是"设备没注册"这件事的投影。**不能用它来证明"没有网络"**，只能用来说明"没有网卡"。

## 为什么裸 IP 也连不上

实测 `http://203.0.113.10/` → `code 7`，59 ms。

`connect()` 的流程是：查路由表 → 找到出口设备 → 发包。没有已注册设备 → 路由表为空 → 立即返回 `ENETUNREACH`/`EHOSTUNREACH` → 被绑定层翻译成 `code 7`。

- 59 ms 说明**没有发生任何真实网络交互**（不是超时）
- 加 `Host: example.com` 头不改变结果（P1 vs P1+H 完全一致），进一步证明请求没出网卡

所以"用 JS shim 把域名换成 IP"这条路**不成立**——换成 IP 也一样连不上。这个方案在早期被提出过，后来被 P1 探针否掉了。

## interconnect 在这条链路里的位置

`interconnect` 是小米的跨设备互联框架。在 9 Pro 的固件包里它只有 17 KB（`interconnect.res`），在 10 Pro 的 `vela_ap.bin` 里能看到 `miwear-server`、`Start quickapp proxy server` 等串。

| 层 | interconnect | Miwear NET |
|---|---|---|
| 用途 | 通用设备间消息 | **专门传 IP 包** |
| 传输 | BLE | BLE |
| 手环侧接收者 | interconnect 服务 | `app_net.c` |
| 需要什么 | 无需驱动 | **需要 `/dev/tun`** |

两者走同一条 BLE 链路，但是**不同的上层协议**。用户想绕开的是"第三方网桥"，而 Miwear NET 是官方 App 自带的——这正是用户想要的形态，只是它缺了驱动。

## 一次失败连接的完整时间线

```
T+0.000  手机 BLE 连上手环
T+0.5    NetProxyComponent onConnectSuccess, support = true
T+1.0    NetProxyManager.start()  ← 第一次 jniContext = 0，空转
T+2.0    sync Phone NetWorkState to Device（约 30 次）
T+48     第二次 start()，jniContext 非零，started = true
T+48.1   手环收到连接状态更新
T+48.1   app_net_connect_state_update → net_tun_open → open("/dev/tun") → ENOENT
T+48.2   日志：tun open fail
T+56     BLE 掉线，errorCode 2011/2012
```

断点在 `T+48.1`。
