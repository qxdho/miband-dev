# 06 · 内核模块系统

## 本文讲什么

10 Pro 能不能在运行时加载一段自己写的内核代码？如果能，格式是什么、怎么被加载、能调用哪些固件函数、有什么坑。**这一篇决定整个项目是否可行**——如果模块加载不成立，补 `/dev/tun` 就只能改固件重刷，而固件有签名，等于死路。

**结论**：模块系统是齐备的。`modlib` + `insmod` 在固件里，加载器参数有完整记录，**创建 `/dev/tun` 所需的全部内核 API 都已被精确定位**（`register_driver`、`netdev_register`、`netdev_input`、`ipv4_input`、`net_lock`…）。风险不在"有没有能力"，而在"这套 ABI 在真机上从未被验证过"。

## NuttX 的 modlib 是什么

`modlib` 是 NuttX 的可加载模块子系统，对应 Linux 的 `.ko`：

| 能力 | 对应命令 |
|---|---|
| 加载 ELF 可重定位目标文件 | `insmod <path> <name>` |
| 执行重定位 | 加载时由 modlib 完成 |
| 调用模块构造函数 | 扫描 `init_array` |
| 卸载 | `rmmod <name>` |
| 查看已加载 | `lsmod` |

### 10 Pro 上的证据

| 证据 | 计数 |
|---|---:|
| `nuttx/libs/libc/modlib/` 源文件路径串 | 多个 |
| `modlib` | 16 |
| `modlib_symtab` | 1 |
| `insmod` / `rmmod` / `lsmod`（NSH 命令表） | 1 / 1 / 1 |

9 Pro 这些全是 0。**这是 10 Pro 唯一一个 9 Pro 完全不具备的能力**，也是整个方案的立足点。

## 模块文件格式

Canopus 的 target pack 把加载器参数完整记录了下来（`target.toml` 的 `[loader_profile]`），这是本文档里关于模块格式最可靠的一手资料：

| 字段 | 值 | 含义 |
|---|---|---|
| `elf_class` | `32` | ELF32 |
| `elf_machine` | `ARM` | `EM_ARM` |
| `elf_type` | `ET_REL` | **可重定位目标文件**，不是可执行文件 |
| `endianness` | `little` | 小端 |
| `constructor_discovery` | `init_array` | 构造函数从 `.init_array` 段找 |
| `symbol_imports` | **`none`** | **不允许导入符号**（关键，见下） |
| `max_size` | `0` | 无大小上限 |
| `alignment` | `4` | 4 字节对齐 |
| `module_name_rules` | `^[a-zA-Z0-9_]+$`，作为 `argv[2]` 传给 `insmod` | 名字只能用字母数字下划线 |
| `load_command` | `insmod <path> <name>` | |
| `unload_command` | `rmmod <name>` | |
| `persistent_autoload` | `false` | **重启后不自动加载** |

目标架构：

| 项 | 值 |
|---|---|
| `architecture` | `armv8-m.main` |
| `cpu` | `cortex-m33` |
| `instruction_set` | `thumb2` |
| `float_abi` | `soft` |
| `module_abi` | `1` |
| `relocation_profile` | `best1503-v1` |

**编译目标就是 Cortex-M33 + Thumb2 + 软浮点**，用 `arm-none-eabi-gcc -mthumb -mcpu=cortex-m33 -mfloat-abi=soft -fPIC -c` 这一类参数即可产出。

## 加载流程

```
insmod /data/xxx.ko tun0
   │
   ├─ 1. 读 ELF 头，校验 ET_REL / EM_ARM / ELF32
   ├─ 2. 分配内存，把各 SHF_ALLOC 段拷进去
   ├─ 3. 处理重定位表（见下）
   ├─ 4. 解析外部符号 —— 本平台 symbol_imports = none，这一步是空操作
   ├─ 5. 遍历 .init_array，逐个调用构造函数
   └─ 6. 把模块记入已加载列表（lsmod 可见）
```

模块的构造函数就是入口。TUN 驱动应当在这里做两件事：

```c
static void tun_init(void) {
    register_driver("/dev/tun", &g_tun_fops, 0666, NULL);  // 建节点
    netdev_register(&g_tun_dev, NET_LL_ETHERNET);          // 注册网卡
}
```

`persistent_autoload = false` 意味着**每次重启都要重新 `insmod`**。这对研究阶段无所谓，但对"日常可用"是个硬伤——得靠 Canopus/Chaos 这类加载器在开机时自动跑一次。

## 重定位支持

`[loader_profile.relocations]` 列出了 modlib 认得的重定位类型：

| 名称 | `r_type` | 用途 | 备注 |
|---|---:|---|---|
| `R_ARM_NONE` | 0 | 空操作 | 接受 |
| `R_ARM_ABS32` | 2 | 32 位绝对地址 | 已验证 profile，设备级验证待做 |
| `R_ARM_REL32` | 23 | 相对地址 | 同上 |
| `R_ARM_TARGET1` | 38 | 按 ABS32 处理 | |
| `R_ARM_PREL31` | 42 | `.ARM.exidx` 用 | 已验证 |
| `R_ARM_THM_MOVW_ABS_NC` | 47 | Thumb `movw` 立即数低半 | 已验证 |
| `R_ARM_THM_MOVT_ABS` | 48 | Thumb `movt` 立即数高半 | 已验证 |
| `R_ARM_THM_CALL` | 10 | 模块内 `BL` | 设备级验证待做 |
| `R_ARM_THM_JUMP24` | 30 | 模块内条件跳转 | 设备级验证待做 |

**注意备注列**：好几项写着"exact device gate pending"——即**这套重定位在真机上没跑过**。这是整个方案最大的技术风险，不是理论问题，是"第一次 `insmod` 可能直接崩"的问题。

## `symbol_imports = "none"`：最关键的一条

这一条决定了模块怎么写。

正常情况下，模块里调用固件函数是这样的：

```c
extern int netdev_register(void *dev, int type);
netdev_register(&dev, 1);          // 编译器生成 R_ARM_THM_CALL + 符号引用
```

加载器再去固件的符号表里查 `netdev_register` 的地址，把调用补上。

**但这台机器不允许导入符号。** 固件的符号表是剥掉的（[03 篇](03-系统架构.md)里 `netdev_register` 字符串为 0 就是这个原因）。

于是只能**把地址硬编码进去**。Canopus 的做法是生成一层"veneer"（贴片函数）：

```c
// generated/canopus_veneer.h:292
typedef int (*canopus_fw_netdev_register_fn)(void *, int);
static inline int canopus_fw_netdev_register(void * a0, int a1) {
    return ((canopus_fw_netdev_register_fn)(uintptr_t)0xc1fc215)(a0, a1);
}

// generated/canopus_veneer.h:318
typedef int (*canopus_fw_register_driver_fn)(const char *, const void *, uint32_t, void *);
static inline int canopus_fw_register_driver(const char * a0, const void * a1, uint32_t a2, void * a3) {
    return ((canopus_fw_register_driver_fn)(uintptr_t)0xc1aff61)(a0, a1, a2, a3);
}

// generated/canopus_veneer.h:463
typedef int (*canopus_fw_unregister_driver_fn)(const char *);
static inline int canopus_fw_unregister_driver(const char * a0) {
    return ((canopus_fw_unregister_driver_fn)(uintptr_t)0xc1b002d)(a0);
}
```

`static inline` + 常量地址 → 编译成 `movw/movt` + `blx`，**没有任何外部符号引用**，`symbol_imports = none` 就不碍事了。

> 地址末位是奇数（`0xc1fc215` 而不是 `0xc1fc214`）是 **Thumb 位**：Cortex-M 只有 Thumb 指令，函数指针最低位为 1 表示"按 Thumb 解码"。写 veneer 时必须带上，否则会以 ARM 模式跳转直接 HardFault。

**代价**：这些地址和固件版本强绑定。换一个固件版本（比如 `3.101.036`）就得换一整套地址。target pack 正是按 `firmware_sha256` 分目录存放的，就是为了处理这件事。

## 字符串 ≠ 函数

这是本项目里代价最大的一个方法错误，值得单独说。

早期判断"10 Pro 有没有某个能力"的方法是**在固件里数字符串**：

```bash
node -e '...b.indexOf("netdev_register")...'   # → 0
```

`netdev_register` 出现 0 次，于是得出"10 Pro 没有网络设备注册入口"。

**这个推理是错的。** 字符串在固件里的来源主要有三类：

| 来源 | 编译后是否保留 |
|---|---|
| 日志格式串（`printf("...")`） | ✅ 保留 |
| 断言里的表达式文本（`ASSERT(cond)`） | ❌ 关掉 `NDEBUG` 就没了 |
| 符号名（调试信息） | ❌ 被 strip 掉 |

一个函数**存在**但它的名字**不存在**，是完全正常的——尤其当它只在断言里被提到时。

Canopus 的 target pack 用 IDA 对**同一个 `firmware_sha256`**（`51930767…56ec`）做了精确恢复，给出：

```
netdev_register  @ 0xc1fc214   int(void *, int)   STATIC_RECOVERED / APPROVED
```

**函数在。** 之前那条"缺注册入口"的结论已被推翻（记录在[附录](附录-研究历程与误判.md)）。

> **正确的用法**：字符串计数可以用来**否定**"某功能有活跃的调用路径"，但不能用来**否定**"某函数存在"。要证明函数存在，必须看反汇编或恢复出的符号表。

## 已恢复的符号

target pack 里有 **259 条符号记录**，其中 55 条被包成 veneer。和网络驱动直接相关的：

| 符号 | 地址 | 原型 | 用途 |
|---|---|---|---|
| `register_driver` | `0xc1aff60` | `int(const char*, const void*, uint32_t, void*)` | **创建 `/dev/tun` 节点** |
| `unregister_driver` | `0xc1b002c` | `int(const char*)` | 删除节点 |
| `netdev_register` | `0xc1fc214` | `int(void*, int)` | **注册网卡** |
| `netdev_input` | `0xc1fc9f4` | `int(void*, void*, int)` | 收包注入协议栈 |
| `ipv4_input` | `0xc1f95c8` | `int(void*)` | 直接把 IPv4 包喂给协议栈 |
| `net_lock` / `net_unlock` | — | — | 网络栈加解锁 |
| `devif_poll` | — | — | 轮询发送 |
| `socket` / `sendto` / `setsockopt` / `read` / `write` / `close` | — | POSIX 语义 | 模块内可直接用 |
| `heap_malloc` / `heap_zalloc` / `heap_free` / `heap_mallinfo` | — | — | 堆分配 |

### 仅从这张表就能看出

写一个 TUN 驱动需要的**全部**要素都在：

1. `register_driver` → 让 `/dev/tun` 存在（解决 `ENOENT`）
2. `netdev_register` → 让 TCP/IP 栈有一个出口设备（解决"无路由"）
3. `netdev_input` / `ipv4_input` → 把从 BLE 收到的包注入协议栈
4. `read` / `write` 对应的 `file_operations` → 让 `app_net.c` 能 `open("/dev/tun")` 并读写
5. `heap_*` → 缓冲分配

`app_net.c` 那边的代码一行都不用改。

## 做模块需要什么

### 最小验证模块（先证明加载能跑通）

```c
// hello.c — 只做一件事：证明模块被加载、构造函数被调用
#include <stdint.h>

typedef int (*log_fn)(const char *);
static int klog(const char *s) {
    return ((log_fn)(uintptr_t)0xc130d21)(s);   // 固件里的日志函数
}

__attribute__((constructor))
static void hello_init(void) {
    klog("[hello] module loaded\n");
}
```

编译：

```bash
arm-none-eabi-gcc -mthumb -mcpu=cortex-m33 -mfloat-abi=soft \
  -Os -fPIC -fno-plt -nostdlib -c hello.c -o hello.o
arm-none-eabi-ld -r -Ttext=0 hello.o -o hello.ko
```

预期结果：`insmod /data/hello.ko hello` 之后，日志里出现 `[hello] module loaded`。

**这一步没跑通之前，不要写完整驱动。** 它同时验证了四件事：模块格式、重定位、构造函数发现、`symbol_imports=none` 下的硬编码调用。

### TUN 驱动（真正解决问题）

| 组成 | 内容 | 大概行数 |
|---|---|---|
| `file_operations` | `open` / `close` / `read` / `write` / `ioctl` / `poll` | ~150 |
| TUN 收发环形缓冲 | 读走 `app_net.c` 写进来的包，写回从 BLE 收到的包 | ~150 |
| `netdev` 注册 | 填 `struct netdev_ops` 里的 `rmmac`（发送）回调 | ~100 |
| `ioctl` 处理 | `TUNSETIFF`、`SIOCGIFMTU`、`SIOCGIFHWADDR` | ~80 |
| 初始化 | `register_driver` + `netdev_register` | ~40 |
| **合计** | 精简版（只支持 TUN 用法） | **500–700 行 C** |

代码体积估算 3–6 KB，运行内存 2–6 KB，`.ko` 文件 10–20 KB。

## 限制与风险

| 风险 | 说明 | 严重度 |
|---|---|---|
| **ABI 未在真机验证** | target pack 自己标注 `exact 3.101.043 device gate pending` | 🔴 高 |
| **地址与版本绑定** | 换固件版本全部失效 | 🟡 中（可重新恢复） |
| **`struct netdev` 布局未知** | 没有头文件，字段偏移要靠反汇编推 | 🔴 高 |
| **`file_operations` 布局未知** | 同上 | 🔴 高 |
| **重启失效** | `persistent_autoload = false` | 🟡 中 |
| **模块名规则严格** | 只能 `[a-zA-Z0-9_]+` | 🟢 低 |
| **崩溃即变砖风险** | 内核态错误可能直接死机；但模块在 RAM，重启可恢复 | 🟡 中 |
| **`netdev_register` 的第二参数语义** | `int` 是什么（链路层类型？设备号？）未确认 | 🟡 中 |

最后一条值得展开：`netdev_register(void *dev, int type)` 的 `int` 在 NuttX 不同版本里可能是 `int lltype`（链路层类型，如 `NET_LL_ETHERNET`），也可能是别的。搞错了会注册成功但收发包异常——这种 bug 最难查。

## 未决问题

| 问题 | 状态 |
|---|---|
| 这套 modlib 重定位在 3.101.043 真机上是否真的能跑 | ❓ **最关键未验证项** |
| `struct netdev` 的完整字段布局 | ❓ 需反汇编 `netdev_register` 内部 |
| `struct file_operations` 的字段顺序 | ❓ 需反汇编 `register_driver` 或参照 NuttX 版本 |
| `netdev_register` 第二参数的确切含义 | ❓ |
| 模块里能否安全创建线程（`pthread_create_internal` 已恢复） | ⚠️ 有符号，未验证 |
| 谁来触发 `insmod` | ⚠️ Canopus 安装器的 Lua 表盘可以（见 [07 篇](07-Canopus.md)） |
