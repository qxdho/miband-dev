## 3. P0（会破坏数据/进不了系统）

### C01 注册表改造在"解析已截断"的状态下仍会回写，静默丢条目
`supervisor/src/appmgr.rs:1776-1785`（`move_vis_to_hide`）、`:1761`（`remove_all_pkg`）

`write_blocked()` 检查的是**上一次 `reload()` 时的状态**，之后 `capture()` → `parse_registry()` 会重新读盘：
`scan_object` 在第 41 个对象或包名非法时置 `TRUNC`，但 `parse_registry()` 仍返回 0，于是 `capture()` 返回 true，
`serialize()` 只序列化已登记的条目 → 未登记对象被**静默丢弃**，随后 `write_file()` 落盘。

这直接违反文件自己写的红线（`appmgr.rs:29-32`：「解析被截断时绝不回写」）。
触发条件：上次 reload 之后固件装了新应用（或上次写盘被中断留下无 `package` 的残项），用户再隐藏/显示任一应用。

**修**：`capture()`/`parse_registry()` 返回后重新 `write_blocked()`；或让 `capture()` 在 `TRUNC`/`OVERSIZE` 时失败，
`serialize()` 里也拒绝截断态。`remove_all_pkg` 连这道检查都没有，需一并加。

## 4. P1

### C02 坏 `.ko` 能通过构建闸门（校验脚本不会失败）
`tools/verify_chaos_ko.py:46-59`

脚本把未定义符号、`.init_array` 缺失、重定位类型**只打印不判定**，文件到 59 行直接结束，没有 `sys.exit(1)`。
`build_ko.sh:14-15` 明确警告过"`.text` 为 0 的镜像加载器会一声不吭地装成功"，而校验脚本连 `.text` 大小都不检查。
CI 只跑 `build_ko.sh`（`.github/workflows/build.yml`），于是这类坏包会一路进入 release。

**修**：未定义符号非空、`.text`/`.init_array` 缺失或为 0、`e_entry` 非预期、总大小 ≥256KB 一律 `raise SystemExit(1)`；
顺带把 256KB insmod 上限也纳入检查。

### C03 主模块部署是"原地截断 + 不看返回值 + 无回读"
`installer/chaos_installer.lua:202-210`（`stage_resource`），用于 `:479` 流水线第一步（部署 `sup.ko`）

```lua
local f = io.open(dest, "wb")            -- 先毁掉旧模块
local wok, wres = pcall(f.write, f, c)   -- 只判断"有没有抛错"，不判断返回 nil（ENOSPC/短写）
if not wok or not cok then return false, "write failed" end
return true
```
而同一个文件里已有做回读比对的 `write_file()`（`:253-262`），却没被这条流水线使用。
断电/写失败 → 留下半截 `sup.ko` → 下次开机 `/data/rc.d/chaos.sh` 无条件 `insmod` 这半截模块 → 可能进不了系统。

**修**：写 `dest.tmp` → `close` → 回读比对长度（最好加哈希）→ `rename` 覆盖；该步改走 `write_file()`。

### C04 没有固件指纹/版本门，而开机脚本无条件 insmod
`installer/chaos_installer.lua:283-297`（`build_chaos_sh`）、`supervisor/src/lib.rs:198-230`（`chaos_ctor` 直接调固化地址）

安装器全程没有任何设备固件版本校验（`grep version` 只命中模块自报的 `STATUS_VERSION`），
生成的 `/data/rc.d/chaos.sh` 是 `set +e` + `insmod /data/chaos/chaos_sup.ko` + 两次 dd，没有任何前置条件；
模块 `ctor` 一进来就调 `0x0C1AFF61` 等固化地址。把 3.101.043 专用包装到别的固件上 = 开机即 HardFault = 重启循环。
README 只用文字警告"其它版本不要使用"，代码里没有任何拦截。

**修**（两层，成本都很低）：
1. 模块侧：`ctor` 第一步先校验一段已知镜像字节（例如 `0x0C1AFF61` 处指令或其前后 8 字节魔数），不符则直接返回、不注册驱动、不建定时器；
2. 安装器/rc 侧：insmod 前用 `getprop`（安装器已有这条通路，见 `:127-160` 的语言检测）读固件版本属性，不符就跳过并写 `autostart.log`。

### C05 `panic=abort` + `loop{}` 的 panic handler = 任何 panic 都让设备永久死机
`supervisor/src/lib.rs:253-254`

```rust
#[panic_handler] fn panic(_: &PanicInfo) -> ! { loop {} }
```
`Cargo.toml` 里 `panic = "abort"`。编译期断言之外，运行期 panic 面仍在（切片越界、除零），
一旦触发：设备不重启、不留任何痕迹，用户只会看到"手表卡死"，只能强制重启。

**修**：panic handler 里先尽力把 `PanicInfo` 写进 `/data/chaos/panic.txt`（能开文件就写），
再触发系统复位（`0xE000ED0C = 0x05FA0004`，或 `fw_api` 里已有的复位路径），把"死机"降级成"重启"。

### C06 字体包不校验内容，且能覆盖正在使用的槽
`installer/font_pack.lua:237-262`、`:315`；`supervisor/src/ipc.rs:371-381`、`:99-108`

`io.open(FONT_RESOURCE)` 直接搬到 `/data/chaos/font/st<N>.ttf`：无魔数、无长度、无 sfnt 解析；
ko 侧 `font_slot_file_ok` 也只 open/close。而 `index_read()` 在 index.txt 缺失时返回空表，
`index_alloc()` 可能分配出**当前在用**的槽，`io.open(..., "wb")` 在校验之前就把活着的字体文件截断了——
这正是该文件头注释（`:6-10`）明令禁止的"让还活着的老脸读到别人的字节"。
结果：全 UI 字体异常，最坏是 LVGL 拿损坏字体建脸时崩。

**修**：① 写入前校验 sfnt 头（`0x00010000`/`OTTO`/`true`/`ttcf`）与最小长度；
② 拒绝 `job.slot == cur`（除非是覆盖自己那份）；
③ 写 `st<N>.ttf.tmp`，等 0x30 收到 ACK 再 rename。
④ ko 侧 `commit` 之前也做同一套头校验（现在只 open/close 就 `commit` + `remember_font` 持久化，坏文件会跨重启生效）。

> 注：固件侧**没有**任何二进制 TTF/glyph 解析器（`index.txt` 是定长文本清单，输入只有这份清单、16 字节命令帧、
> 固件自有 RAM 结构），所以这里的风险不是"解析越界"，而是"发布前不校验 + 发布后不可撤回"。

### C07 注册表原地改写，无 temp/无备份，短写就回滚出"两边都没有"
`supervisor/src/appmgr.rs:1692-1704`（`write_file`）

删除条目时内容是**左移**的，部分写入会留下旧尾巴；尾部空格填充只能救"成功的短序列化"，救不了"写失败"。
下一轮启动见 `PARSE_BAD` 就转只读，没有恢复路径。`close()` 返回值也未检查。
更糟：`move_vis_to_hide` 第二步失败会触发回滚删除，条目可能**两个文件里都没有**。

**修**：`<path>.new` → 回读校验 → rename；保留 `<path>.bak` 直到校验通过；任何短写/负返回视为整体失败，不做半截回滚。

### C08 `remove_all_pkg` 把"读不到/解析失败"当成"已删干净"
`supervisor/src/appmgr.rs:1765`

`capture()` 对"文件不存在""打不开""解析失败"统一返回 false，调用方 `if !capture(...) { return true; }`
一律视为删除完成。若第一次写成功后回读失败，刚追加进 `apps.json_hide` 的副本会留下、可见副本却没删 →
同一包名同时出现在两个文件 → `E_DUP` → 按代码自己的注释（`:1759-1760`）固件会建两个桌面记录、退出时二次释放（黑屏）。

**修**：`capture` 区分 `Found / NotFound / Err`，只有 `NotFound` 算完成，`Err` 向上传播让调用方回滚追加。

> C07/C08 与 C01 同属"注册表写路径"，建议一起改（同一套 temp+verify+rename 助手即可全部覆盖）。

### C28 删除"正在使用的字体"时，清单与文件在回退没成功前就已不可逆
`supervisor/src/font_apply.rs:632-636`、`:708-710`；`supervisor/src/font_list.rs:563`、`:587`

建脸失败的样式会被跳过（只把 `FA_C_FACE0` 加一，**没有任何地方用它当门**），
而 `apply_finish()` 无条件清 `FA_REVERT`；删除流程的状态 11 只等 `revert_busy()`（= `FA_REVERT`）就进状态 2 执行
`fw_api::fs_remove(p)`。于是在"个别样式回退失败"时，字体文件被删、那些样式仍持有"按需回读该文件"的脸 ——
正是代码注释里写的红线。一次 `mfont_create` 的瞬时失败（内存紧张/管理器预热）就够触发。

**修**：`FA_REVERT` 只在 `FA_C_FACE0 == 0 && FA_C_WR == FA_JOB_N` 时才清；把"回退失败"暴露给删除流程，
状态 11 遇到失败必须中止删除并给可见提示，而不是继续。

### C32 所有"隐藏行"的调用都是空操作（`obj_set_hidden` 其实是 `lv_obj_clear_state`）
`supervisor/src/fw_api/gfx.rs:70-73`；调用点 `supervisor/src/ui.rs:119`、`:280`、`supervisor/src/page.rs:1143`

```rust
pub unsafe extern "C" fn obj_set_hidden(obj: Obj, hidden: u32) -> Obj {
    let f: unsafe extern "C" fn(Obj, u32) -> Obj = transmute(0x0C58_8519usize);
    f(obj, hidden)
}
```
`gfx.rs:65-69` 自己写着「同一个入口的真身是 `lv_obj_clear_state`，**它不隐藏任何东西**，页 7/8/9 的行显隐实际没有发生隐藏」。
后果：表盘页 8/9 上超出窗口的行、应用管理页超窗口的行都不会隐藏（LVGL v9 已删除 `lv_obj_set_hidden`，正解是 `lv_obj_add_flag(obj,1)`）。

**修**：`obj_set_hidden(0/1)` 改实现为 `obj_add_flag(obj, LV_OBJ_FLAG_HIDDEN)` / `obj_clear_flag(...)`
（现有壳 `0x1C028BD9`/`0x1C028C85` 就在 `gfx.rs:605-615`），`obj_clear_state` 只留给 `page.rs:533` 的 FOCUSED 清除。

### C39 `APP_FG` 在 pause 清、在 resume 不恢复，把字体跑批的安全门反向打开
`supervisor/src/ui.rs:417`（清）、`:48`（唯一置 1 处）、`:362-411`（resume 未置）；`supervisor/src/font_apply.rs:540`

`chaos_on_pause` 写 `APP_FG=0`，`chaos_on_create` 写 1，`chaos_on_resume` **不写**（`state.rs:369` 的注释明确要求 resume 置、
pause/destroy 清）。息屏唤醒若没有重建页面实例，模块就一直认为自己在后台；而字体逐对象改写在 `font_apply.rs:540`

**修**：`chaos_on_resume` 里设 `FG_PAGE` 之后立刻 `st_wr!(APP_FG, 1)`，并在 `chaos_on_destroy` 里清零。

### C40 `WfMgmtPage` 把栈上缓冲当行文本传下去（悬空指针）
`supervisor/src/page.rs:1176-1189`

```rust
let mut tbuf: [u8; 88] = [0; 88];
shake_toggle_text(tbuf.as_mut_ptr());
let text = core::slice::from_raw_parts(tbuf.as_ptr(), tlen + 1);
```

本仓库自己的硬规则是"行控件的文本指针必须一直有效"（`icon_apply.rs:163`、`appmgr.rs:131`），其它页都用 `WATCH_LINES`/`FL_LINES`/`IC_LINES` 静态缓冲，

### C41 日期设置页（pid 3）仍在跑"目录页"的 resume 分支
`supervisor/src/ui.rs:377-387`

`if pid == 3 { DIR_DEPTH = pid-1; load_dir(); }`，但 `PAGE_TABLE[3]` 现在是 `&PAGE_DATE_MD`（`page.rs:2253`，`DATE_MD_PID=3`）。
`PATH_STACK` 只有退役的文件管理页会填，于是 `load_dir()` 拿着全零路径去 `opendir`，还顺手覆盖 `DIR_DEPTH/DIR_WIN/DIR_COUNT/DIR_ERR`。
紧挨着的注释已经记录过同类误用："点「时间设置」立即崩"——现在每次进日期设置都会走这条路。

**修**：删掉这段 `if pid == 3`（已无目录页可达），或改成显式的"当前页确实是目录页"判据。

### C42 `chaos_on_resume` 不校验页面存活就 `render_page`
`supervisor/src/ui.rs:411`；对比 `supervisor/src/ui.rs:61-70`（`page_is_live`）

`render_page(pid)` 内部只查 `PAGES[pid].root != 0`（`ui.rs:220-221`），而其它所有渲染路径（行分发、tick、render_req、表盘自愈）都以
`page_is_live`（读描述符 +0x30）为门。唤醒时若固件已拆掉对象树却没回调可选的 `ui_destroy`，就会对着已释放的 LVGL 内存建标题/内容。
且 resume 开头自己就承认"描述符可能不是本页的（唤醒时固件换了编码）"。

**修**：`render_page(pid)` 之前加 `if !page_is_live(pid) { return 0; }`。

## 7. 系统性风险（比单点 bug 更值得看）

| 指标 | 数值 | 含义 |
|---|---|---|
| `unsafe fn` | 545 | API 面几乎全是 unsafe，调用点自行负责不变量 |
| `static mut` | **439** | 全局可变状态是主要设计范式；跨上下文共享（定时器 ↔ syscall）无类型级约束 |
| `transmute` | 156 | 多为"地址→函数指针"，一旦基址漂移即跳野指针 |
| `as *mut` / `as *const` | 149 / 447 | 指针算术密集 |
| `.unwrap()/.expect()/panic!` | **0** | 这条做得很好：panic 面被压到只剩编译期断言 |
| 测试 | **0** | 所有行为保证都靠真机试错与注释 |

**评价**：`unsafe` 密度是被逆向任务本身逼出来的（要和固件的裸地址、链表、LVGL 对象打交道），
防御写法（`safe_ptr` 白名单、`guard<512` 链表上限、`is_child_of` 校验、失败回退原图标、A/B 槽世代计数）也在，
单点质量不低。**真正缺的是"错误发生时谁兜底"**：unsafe 代码没法证明正确，所以必须有
①会失败的闸门 ②可恢复的写盘 ③能自愈的启动（指纹门 + panic 重启）。
