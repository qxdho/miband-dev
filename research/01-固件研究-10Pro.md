# 01 · 固件研究（10 Pro）

## 本文讲什么

小米手环 10 Pro 的固件包长什么样、里面有哪些东西、装到哪儿、以及**怎么把那堆裸字节变成可分析的地址**。后面所有固件层面的结论都建立在这一篇的地址换算规则上。

**结论**：`firmware/10pro/fw.bin` 是标准 ZIP；真正的系统在 `vela_ap.bin` 里，它**不是 ELF**，而是一个 12 字节头 + 裸 ARM 镜像，同一份字节被映射到两个虚拟地址（代码 `0x0C000000`，数据 `0x2C0C0000`）。分区布局由包内的 `ota.sh` 明文写死。

## `ota.sh`：分区布局

这是整个固件包里信息密度最高的 937 字节。原文（去掉重复的进度设置）：

```sh
setprop ota.progress.current 30
setprop ota.progress.next 95
setprop ota.progress.status 1
setprop ota.progress.size 171755520
dd if=/ota/vela_resource.bin of=/dev/resource bs=32768 verify

setprop ota.progress.size 451468
dd if=/ota/vela_bl2.bin of=/dev/bl2 bs=32768 verify

setprop ota.progress.size 13795728
dd if=/ota/vela_ap.bin of=/dev/ap bs=32768 verify
```

### 从这 20 行能读出的东西

| 读出的信息 | 依据 |
|---|---|
| 分区设备节点是 `/dev/ap`、`/dev/bl2`、`/dev/resource` | `of=` 参数 |
| 安装到 `/ota/` 目录 | `if=/ota/...` |
| 块大小 32 KiB 且带读回校验 | `bs=32768 verify` |
| 任何一步失败就 `reboot`（回滚到旧固件） | `if [ $? -ne 0 ]; then reboot` |
| 进度通过 `ota.progress.*` 属性上报给 UI | `setprop` 序列 |
| **`vela_ota.bin` 不由 `ota.sh` 写入** | 脚本里没有它的 `dd` |

最后一条值得注意：包里带了 `vela_ota.bin`，但安装脚本只写三个分区。说明 OTA 升级器自己由另一条路径（bootloader 或 BL2）处理，或者它只是给"从更老版本升级"用的跳板。

### 分区表（推导）

| 分区节点 | 镜像 | 大小 | 内容 |
|---|---|---:|---|
| `/dev/bl2` | `vela_bl2.bin` | 451,468 | 二级引导 |
| `/dev/ap` | `vela_ap.bin` | 13,795,728 | 应用处理器固件 |
| `/dev/resource` | `vela_resource.bin` | 171,755,520 | 资源 |

`/dev/ota`、`/dev/ota_data`、`/dev/factory`、`/dev/efuse`、`/dev/otp` 等节点在手环运行时的日志与挂载表里都能看到，但它们不由这个包写入。

> 这解释了为什么"给手环装第三方东西"必须发生在运行时：固件包有签名，且只能整体替换三个分区。任何改动都得走 `/data` 分区 + 模块加载。

## `vela_ap.bin` 镜像格式

### 它不是 ELF

```
$ readelf -h vela_ap.bin
（无输出）
```

`readelf`、`objdump` 都认不出来。文件头是这样：

```
000000  ff ff ff ff  00 00 05 00  00 00 00 00  24 80 de 28
000010  14 48 00 47  01 f0 6e fd  13 48 80 f3  08 88 13 48
000020  80 f3 0a 88  00 20 80 f3  14 88 bf f3  6f 8f 00 f0
```

| 偏移 | 内容 | 解释 |
|---|---|---|
| `0x00` | `ff ff ff ff` | 头部魔数 / 未初始化标记 |
| `0x04` | `00 00 05 00` | 版本或块数 |
| `0x08` | `00 00 00 00` | 保留 |
| `0x0c` | `24 80 de 28` → `0x28de8024` | **ARM 向量表第 0 项：初始栈指针**（约 685 MB，合理） |
| `0x10` | `14 48 00 47` | Thumb 指令 `ldr r0,[pc,#0x50]` / `bx r0`，复位向量 |

即：**12 字节自定义头 + 从 `0x0c` 开始的裸 ARM 向量表**。没有程序头、没有节表、没有符号表——所有分析只能靠字符串和指针反推。

### 地址换算规则（关键）

镜像被映射到**两个虚拟地址**，都相对文件偏移线性：

```
代码地址 = 0x0C000000 + 文件偏移
数据地址 = 0x2C0C0000 + 文件偏移
```

验证（在 `vela_ap.bin` 里搜索字符串地址的 32 位小端引用）：

| 字符串 | 文件偏移 | 按 `0x0C000000` 找 | 按 `0x2C0C0000` 找 |
|---|---:|---|---|
| `/dev/tun` | `0xb55f00` | 0 处 | **1 处 @ `0x6515ac`** |
| `app_net_receive` | `0xc8b650` | 0 处 | **1 处 @ `0x6516b4`** |

即代码里引用字符串用的是**数据别名**，而代码本身在代码别名里执行。这是典型的 XIP 双映射（代码区走指令缓存，数据区走数据缓存/非缓存），只有这样才能让 `ldr r0, =字符串` 拿到正确地址。

> ⚠️ 推断：`0x2C0C0000` 这个"非整"基数提示数据段本身从文件偏移 `0xC0000` 起被加载到 `0x2C000000`。两种说法等价，本文统一用上面的线性式，因为它可以直接用。

### 为什么这个规则重要

固件里所有"这个函数在哪"的问题都要靠它：

1. 找到字符串的文件偏移 `off`
2. 算出数据地址 `0x2C0C0000 + off`
3. 在文件里搜这个 32 位值，找到引用它的位置 `ref_off`
4. **代码地址 = `0x0C000000 + ref_off`**
5. 用 capstone 按 Thumb 反汇编那一段

第 3 步通常会落在**字面量池**里（一长串紧挨着的 32 位地址，前后夹着别的字符串指针），这是 Thumb-2 代码 `ldr rX, =imm` 的实现方式。字面量池本身不是表，只是常量仓库——这点在第 05 篇分析 `remote_net_state_switch` 时会用到，那里正是被误当成"调度表"的地方。

## `vela_resource.bin`

171,755,520 字节，占整个固件包 92%。内容：

- 字体（多语言点阵）
- 表盘资源 `/system/apps/watchface/<id>/resource.bin`
- UI 位图、图标
- 语言字符串表

**分析注意**：这个文件里的"字符串"绝大多数是位图噪声。曾在此文件里搜到 `bnep`，一度被当成蓝牙 PAN 的证据，实际是字体位图里碰巧排列出的 4 个字节。**在 `vela_resource.bin` 里搜到的东西一律不可信，除非能在 `vela_ap.bin` 里也找到。**

## `vela_bl2.bin` / `vela_ota.bin`

| 镜像 | 大小 | 已知信息 |
|---|---:|---|
| `vela_bl2.bin` | 451,468 | 二级引导；`vela_ap.bin` 里能找到引用它的文件名和 `/dev/flash_ap`、`boot2 update`、`update app:%s` 等串 |
| `vela_ota.bin` | 655,360 | OTA 升级器；**不被 `ota.sh` 写入**，用途待查 |

`vela_ap.bin` 内部还嵌了一个 `ZZ~3.1.190` 子容器（偏移 `0x8c9a5`），里面是 `hyn_wxn_firmware.bin`——触摸控制器的固件。这解释了为什么 9 Pro 那个包也是 `60 5A 5A 7E` 开头：那是同一套 BES 打包器产出的容器格式，10 Pro 只是把它整个塞进了 ZIP 里。

## 提取与复现

```bash
# 解包
cd /work/chaos
unzip -o firmware/10pro/fw.bin -d firmware/10pro/fwx/

# 核对完整性
sha256sum firmware/10pro/fw.bin firmware/10pro/fwx/vela_ap.bin
# a4ce8564778624f8287ea91015867dc1725b649fbc10f2c4fa4b6813af7bc4d9  firmware/10pro/fw.bin
# 519307675665e4866d722a8119a98589c397b614ac3294cb87bfc86de45756ec  firmware/10pro/fwx/vela_ap.bin

# 验证地址换算（node，无需额外依赖）
node -e '
const fs=require("fs"),b=fs.readFileSync("firmware/10pro/fwx/vela_ap.bin");
const off=b.indexOf(Buffer.from("/dev/tun","latin1"));
const p=Buffer.alloc(4);p.writeUInt32LE((0x2C0C0000+off)>>>0);
console.log("string@0x"+off.toString(16)+" ref@"+b.indexOf(p).toString(16));
'
```

第二个哈希 `51930767...56ec` 与 Canopus target pack 里 `firmware_sha256` **完全一致**，这是"Canopus 确实支持这台机器这个版本"的硬证据（见 07 篇）。

## 与 9 Pro 的差异

一句话：**容器完全不同，镜像格式相同。**

| 项 | 10 Pro | 9 Pro |
|---|---|---|
| 外层容器 | 标准 ZIP + 签名 | `60 5A 5A 7E` + 版本号，无中央目录 |
| 成员数 | 8 | 237 |
| `vela_ap.bin` | 13,795,728 | 7,775,288 |
| 代码基址 | `0x0C000000` | 同（同一套 BES 工具链） |
