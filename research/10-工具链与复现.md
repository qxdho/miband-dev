# 10 · 工具链与复现

## 本文讲什么

前面各篇的结论都建立在"从固件二进制里把符号和字符串挖出来"这件事上。这一篇把这个过程讲清楚：地址怎么算、脚本各自干什么、标准流程有几步、以及**哪些地方最容易得出错误结论**。

**结论**：核心只有一条规则——**vaddr = 文件偏移 + 基址**，基址有两个：代码段 `0x0C000000`，数据段 `0x2C0C0000`。所有脚本都是这条规则的变体。

## 环境

| 项 | 值 |
|---|---|
| 运行时 | Node.js |
| 反汇编 | `capstone-wasm` |
| 脚本目录 | `/work/chaos/refs/` |
| 固件目录 | `/work/chaos/system/firmware/10pro/fwx/`（10 Pro）、`firmware/9pro/fwx9/`（9 Pro） |

## 地址映射规则

10 Pro 的 `vela_ap.bin` 不是标准 ELF（`readelf` 无输出），但有两段映射：

| 段 | 基址 | 范围 | 内容 |
|---|---|---|---|
| 代码 | `0x0C000000` | 文件 `0x0` ~ `0xCE0000` | ARM Thumb-2 指令 + 字面量池 |
| 数据 | `0x2C0C0000` | 文件 `0x0` ~ 结尾 | 字符串、只读数据、资源索引 |

同一份文件被映射两次。验证方法：对字符串 `S`（文件偏移 `F`）找它的引用——如果某个 32 位字面量 `L` 满足 `L = F + BASE`，那 `BASE` 就是这条规则里的基址。

已有两处交叉验证：

| 字符串 | 文件偏移 | 计算 vaddr | 实测引用位置 |
|---|---:|---|---|
| `/dev/tun` | `0xB55F00` | `0x2CC15F00` | 文件 `0x6515AC`（正文的字面量池） |
| `app_net_receive` | `0xC8B650` | `0x2CD4B650` | 文件 `0x6516B4` |

## 标准流程

### 第一步：解包

10 Pro 的 `firmware/10pro/fw.bin` 是标准 zip，直接展开：

```bash
cd /work/chaos
unzip -o firmware/10pro/fw.bin -d firmware/10pro/fwx/
```

9 Pro 的 `.bin` 是**没有中央目录**的 zip——`unzip` 会失败。必须扫描本地文件头 `PK\x03\x04`，对每一条做 inflate：

```bash
node tools/zip_no_cd.js firmware/9pro/fw9pro.bin firmware/9pro/fwx9/
```

> ⚠️ 这一步踩过坑，见[附录](附录-研究历程与误判.md#误判二9-pro-包里没有应用镜像)。

### 第二步：找字符串

```bash
node tools/table2.js | grep -i "关键词"
```

输出格式是 `vaddr  string`，vaddr 已经按数据段基址算好。

### 第三步：找引用

```bash
node tools/litload2.js firmware/10pro/fwx/vela_ap.bin | grep -i "2cc15f00"
```

这一步回答的是"**有没有代码真的用到这个字符串**"。

> ⚠️ 这一步最容易出错，见[附录](附录-研究历程与误判.md#误判三字符串计数-0-函数不存在)。

### 第四步：反汇编确认

```bash
node tools/dis.js 0xc651500 0xc651600
node tools/region.js 0xc651700 0xc651770
```

看这个地址到底是**代码**、**字面量池**、还是**分派表**。三者的区别见下方"坑二"。

### 第五步：判定

| 观察 | 结论 |
|---|---|
| 字符串存在 + 有代码引用 + 引用点是函数入口 | ✅ 功能存在 |
| 字符串存在 + 只在日志格式串里出现 | ⚠️ 只有埋点，逻辑可能在别处 |
| 字符串存在 + 无任何引用 | ⚠️ 可能是死代码，也可能地址算错 |
| 字符串为 0 | ⚠️ **不能**直接判定"功能缺失"——可能只保留了符号表，字符串被裁掉了 |

## 三个必须记住的坑

### 坑一：无中央目录 ≠ 不是 zip

zip 的解析器通常从文件尾找 `EOCD`（`PK\x05\x06`）。但有些打包器只写本地文件头，不写中央目录。此时 `unzip`、Python `zipfile` 全部报错，但数据是完好的。

**判定方法**：直接扫 `PK\x03\x04`，看每一条的 `compression method` 和 `compressed size` 是否合理、inflate 是否成功。**不要**用"有没有 EOCD"来判断。

### 坑二：字面量池不是分派表

看到 `0x651730` 处连续排列着 `"up"`、`"bt"`、`"remote_net_state_switch"`、`"bt-net"`，很容易以为这是一张"主题订阅表"。

实际上它是**指令流中间的字面量池**——编译器把相邻代码要用的常量集中放在一起。判据：

```bash
node tools/dis.js 0xc651500 0xc651600
```

如果这片地址里混着 `bl`、`ldr`、`cmp` 等指令（尤其是 `bl` 到日志函数），那就是代码 + 字面量池，不是表。

### 坑三：字符串计数不能代替符号存在性

`netdev_register` 在 10 Pro 的 AP 里字符串计数是 **0**，据此我曾判定"驱动注册接口不存在"。

**错。** Canopus 的 3.101.043 target pack 里明确记着：

```
netdev_register   entry 0xc1fc214   callable 0xc1fc215   int(void *, int)
```

函数存在，只是它的名字字符串被裁掉了（固件为省空间剥了符号名，只留地址表）。

**教训**：字符串计数只能证明"存在"，不能证明"不存在"。要证明不存在，得去查符号表/重定位表，或者反汇编目标地址看是不是有效函数序言。

## 复现清单

从零复现本文档全部结论所需的命令：

```bash
cd /work/chaos

# 1. 校验固件
sha256sum firmware/10pro/fw.bin firmware/10pro/fwx/vela_ap.bin
# firmware/10pro/fw.bin        a4ce8564778624f8287ea91015867dc1725b649fbc10f2c4fa4b6813af7bc4d9
# vela_ap.bin   519307675665e4866d722a8119a98589c397b614ac3294cb87bfc86de45756ec

# 2. 解包
unzip -o firmware/10pro/fw.bin -d firmware/10pro/fwx/
node tools/zip_no_cd.js firmware/9pro/fw9pro.bin firmware/9pro/fwx9/

# 3. 找关键字符串
node tools/table2.js | grep -E "tun|netdev|Miwear"

# 4. 找引用
node tools/litload2.js firmware/10pro/fwx/vela_ap.bin

# 5. 反汇编
node tools/dis.js 0xc651500 0xc651600

# 6. 对照 Canopus 符号表
grep -r "netdev_register" projects/canopus/targets/xiaomi-band-10-pro-3.101.043/symbols/
```

## 环境限制

| 限制 | 影响 |
|---|---|
| `readelf` 对 `vela_ap.bin` 无输出 | 不是标准 ELF，只能用自写解析 |
| 无 BES SDK | 无法编译原生模块（除非用 Canopus 的 SDK） |
| 无真机调试通道 | 只能靠日志推断 |
| 固件已剥符号名 | 函数定位只能靠字符串邻近推断 + 交叉验证 |
