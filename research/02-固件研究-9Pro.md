# 02 · 固件研究（9 Pro）

## 本文讲什么

小米手环 9 Pro（`n67cn`）的固件包。它不是 ZIP，没有中央目录，但**里面的 zip 条目是可以直接解出来的**。本文记录容器格式、提取方法、成员清单，以及它和 10 Pro 的镜像层面差异——后者是判断"能不能把 9 Pro 的能力搬到 10 Pro"的基础。

**结论**：9 Pro 的 `vela_ap.bin` 是一份**静态链接**的单体镜像，TUN 驱动、`netdev`、快应用 `fetch` 全编在里面；10 Pro 是**新一代 feature 框架 + 可加载模块**的镜像。两者不是同一代架构，"有/没有某个功能"不能按代码有没有来判断。

## 容器格式

### 文件头

```
000000  60 5a 5a 7e  33 2e 31 2e 31 39 30  00 00 00 00
         `  Z  Z  ~   3  .  1  .  1  9  0
000010  00 00 00 00 ...（补零到 0x40）
```

| 偏移 | 内容 | 解释 |
|---|---|---|
| `0x00` | `60 5A 5A 7E` | BES 打包器魔数（ASCII `\`ZZ~`） |
| `0x04` | `33 2e 31 2e 31 39 30` | **ASCII 版本号 `3.1.190`**，NUL 结尾 |
| `0x0c`–`0x3f` | 全零 | 头部填充 |

这是 BES 芯片厂的标准固件容器。10 Pro 的 `vela_ap.bin` 里也嵌了一个同格式的子容器（`ZZ~3.1.190`，含 `hyn_wxn_firmware.bin` 触摸固件，偏移 `0x8c9a5`），说明两台机器用的是同一套打包工具，只是 10 Pro 在外面又套了一层带签名的 ZIP。

### 关键特征：有局部文件头，没有中央目录

```
$ unzip -l firmware/9pro/fw9pro.bin
（失败：找不到 EOCD）
```

标准 ZIP 的解析依赖文件末尾的 **EOCD（End Of Central Directory）**，再通过它定位中央目录，最后才读局部文件头。这个包**只有局部文件头**，末尾没有 EOCD。

于是产生了一个很自然的误判：**"没有 EOCD，所以不是 zip"**。这是错的。

正确的判据是**看局部文件头**：

```
PK\x03\x04  + 版本(2) + 标志(2) + 压缩方法(2) + 时间(2) + 日期(2)
            + CRC32(4) + 压缩后大小(4) + 原始大小(4) + 文件名长度(2) + 扩展长度(2)
            + 文件名 + 扩展 + 压缩数据
```

只要扫描全文件找 `PK\x03\x04`，逐个解析头部拿到 `压缩后大小`，就能顺着链表把每个条目解出来——**完全不需要中央目录**。

### 提取方法

```
1. 从 0 开始顺序找下一个 PK\x03\x04
2. 读本地文件头：压缩方法（0=存储，8=deflate）、标志位、压缩后大小、原始大小、文件名长度、扩展长度
3. 解压（inflateRaw）
4. 用「实际消耗的输入字节数」跳到下一条记录（而不是用头里的压缩大小，因为可能用了 data descriptor）
5. 写入 firmware/9pro/fwx9/
```

结果：**258 条记录全部解出**，落盘 258 个文件。

> 📌 **同名条目**：有 16 条记录的文件名字面就叫 `resource.bin`（另有重复的 `messages.mo`），大小各不相同——它们大概率是不同表盘的资源，但本地头里没带路径。解包时按 `resource~2.bin` 这样加序号区分，否则会互相覆盖、丢约 13 MB 数据。

> 📌 早期用「先找 EOCD、再读中央目录」的思路时，259 个候选中只有 237 个能通过校验，还有 22 个是数据区里碰巧出现的 `PK` 字节（例如偏移 `0x280112` 处，周围是压缩资源，`inflate` 立即失败）。改成顺序扫描 + 按实际消耗字节跳转后，误报和漏报都消失了。

## 镜像层面：10 Pro vs 9 Pro

在 `vela_ap.bin` 里按字符串计数对比（同一台机器上跑同一个脚本，见 [10 篇](10-工具链与复现.md)）：

| 标记串 | 10 Pro | 9 Pro | 说明 |
|---|---:|---:|---|
| `netdev_register` | **0** | **1** | ⚠️ **只是名字串**，函数本体在 10 Pro 上存在（`0xc1fc214`），见下方更正 |
| `tun%d` | **0** | **1** | 10 Pro 缺 TUN 设备命名 |
| `/dev/tun` | 2 | 2 | 两台的 `app_net.c` 都在找这个节点 |
| `Miwear NET` | 2 | 2 | 隧道客户端两边都有 |
| `app_net_receive` | 1 | 1 | 收包函数两边都有 |
| `TUNSETIFF` | 1 | 1 | ioctl 调用两边都有 |
| `Created Tun` | 1 | 1 | 成功路径日志两边都有 |
| `remote_net_state_switch` | **1** | **0** | 只有 10 Pro 有"远端开关"概念 |
| `fetch_impl` | **11** | **0** | 框架代际差异 |
| `jidl_feature` | **21** | **0** | 框架代际差异 |
| `insmod` | **1** | **0** | 只有 10 Pro 能加载模块 |
| `modlib` | **16** | **0** | 只有 10 Pro 有模块子系统 |

### 怎么读这张表

**第一组（`netdev_register`、`tun%d`）**：9 Pro 有、10 Pro 没有。但这里必须区分**"名字"**和**"函数"**——见下面的更正。

**第二组（`app_net_receive`、`TUNSETIFF`、`/dev/tun`、`Created Tun`）**：两边都有。也就是说 **"打开 TUN 设备"这一侧的代码 10 Pro 是齐的**，缺的是**"把 TUN 注册成网络设备"那一侧**。

> ⚠️ **更正（重要）**：字符串计数只能证明**"这个名字有没有被代码引用"**，不能证明**"函数不存在"**。关掉断言（`NDEBUG`）会把断言里的函数名整个删掉，而函数体照样在。
>
> Canopus 的 target pack 用 IDA 对**同一个 `firmware_sha256`**（`51930767…56ec`）做了精确恢复，给出：
> `netdev_register @ 0xc1fc214`，`STATIC_RECOVERED` / `APPROVED`
>
> 所以 10 Pro **有**网络设备注册 API。缺的不是入口，是**调用它的那段驱动代码**。这条更正把"能不能补"的答案从"不能"改成了"可以"。

第三组（`fetch_impl`、`jidl_feature`、`modlib`）：10 Pro 是新一代框架，9 Pro 是上一代。

### 一个容易搞错的地方

9 Pro 的 `/dev/tun` 出现在**内核 bring-up 的节点列表**里：

```
/dev/urandom|/dev/loop|/dev/ptmx|/dev/utouch|/dev/ubutton|/dev/ukeyboard|/dev/tun|/dev/usensor
```

紧挨着的是 `eth%d|tun%d|netdev/netdev_register.c`。这说明在 9 Pro 上：

- TUN 是在**内核初始化时静态创建**的（`nx_bringup` 里 `register_driver` 注册）
- 所以它的 `/dev/tun` 节点**开机就存在**

而 10 Pro 的 2 处 `/dev/tun` 全部是 `app_net.c` 里的**日志格式串**（`failed to open /dev/tun: %d`），不是创建代码。

> 这就是手环日志里那句 `net_tun_open: failed to open /dev/tun: 2`（errno 2 = ENOENT）的由来：客户端代码齐全、协议齐全、手机侧也连上了，唯独设备节点没人创建。

### 9 Pro 也没有的东西

| 缺失项 | 含义 |
|---|---|
| `bt_sal_*` 全系列 | 蓝牙栈不在 AP 镜像里（在协处理器/别的分区） |
| `bnep` / `panu` / `nap` | 没有蓝牙 PAN 配置文件 |
| `pppd` | 没有 PPP 拨号 |
| `modlib` / `insmod` | **不能加载模块**——所有驱动必须静态编入 |

最后一条很关键：因为 9 Pro 没有模块机制，它的 TUN 驱动是**编译进 `vela_ap.bin` 的机器码**，不是一个可以单独拷贝的 `.ko` 文件。所以"把 9 Pro 的驱动移植到 10 Pro"本质上是**源码级移植**，不是文件搬运。这一点的后果见 [06 篇](06-内核模块系统.md)。

## 教训

> **没有 EOCD ≠ 不是 zip。**
>
> 判断容器格式要看**局部文件头**，不要只看结尾的目录结构。一个包的中央目录可能被裁剪掉（减小体积、防解包），但局部条目仍然完整可解。

这条教训代价不小：因为一开始误判"这个包不含应用镜像"，差点否掉了整条 9 Pro 对照的路线。

## 复现

```bash
cd /dsh/workspace/chaos
node tools/unpack9.js firmware/9pro/fw9pro.bin firmware/9pro/fwx9/     # 局部文件头扫描 + inflateRaw
ls fwx9 | wc -l                            # 223
```

`tools/unpack9.js` 的核心逻辑：

```js
const b = fs.readFileSync(input);
let i = 0;
while ((i = b.indexOf(Buffer.from('PK\x03\x04', 'latin1'), i)) !== -1) {
  const method  = b.readUInt16LE(i + 8);
  const csize   = b.readUInt32LE(i + 18);
  const usize   = b.readUInt32LE(i + 22);
  const nlen    = b.readUInt16LE(i + 26);
  const elen    = b.readUInt16LE(i + 28);
  const name    = b.slice(i + 30, i + 30 + nlen).toString('latin1');
  const dataOff = i + 30 + nlen + elen;
  try {
    const out = method === 0 ? b.slice(dataOff, dataOff + csize)
                             : zlib.inflateRawSync(b.slice(dataOff, dataOff + csize));
    if (out.length === usize && /^[\w.\-/]+$/.test(name)) fs.writeFileSync(path.join(dir, name), out);
  } catch (e) { /* 候选是数据区噪声，跳过 */ }
  i += 4;
}
```
